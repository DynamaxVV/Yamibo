# 讨论助手 Agent 设计与能力集

日期：2026-09-23。范围仅限讨论类帖子。本文承接[对话—知识库改造方案](../对话—知识库改造方案.md)及[讨论类真实数据复核](../讨论类真实数据复核与方案修正.md)，是设计建议，尚未实施。本地离线副本的不完整不代表实际部署的数据或索引状态。

> 用户补充的定时日报、归档与导出完整流程见[日报与归档导出能力修正](../讨论助手—日报与归档导出能力修正.md)。

## 定位

首版维持一个面向用户的 Yamibo 助手，而不是分别建立聊天、检索、研究、归档多个独立 Agent。它接收自然语言委托，分辨**即时讨论问答、定时日报、归档/导出**三类任务，再使用相应的受控能力交付可核查结果。知识库负责资料发现、日报历史与成果保存，Agent 负责理解需求和组织内容。

模型负责理解意图、提出检索词、选择要读的候选、综合不同回复和解释不确定性。程序负责实施讨论范围、预算、读取记录、引用有效性、授权、Job 状态和保存事务。模型的文字不能成为“已授权”“已完成”“已覆盖全部讨论”的依据。

## 一次即时讨论问答怎样运行

1. **识别任务与范围。** 从输入及页面选择中获得任务类型、讨论板块、日期、已选 TID、可用来源与预算。区分“发现模式”（在冻结的讨论分区和时间范围内找候选）与“指定资料模式”（只能读冻结的 TID/PID）。模糊但低风险的筛选条件可以在结果中说明；影响对象或写入范围的歧义应让用户选择。Run 创建时冻结模式与范围，后续修改只影响下一次请求。
2. **发现候选。** 指定资料模式直接读已选帖子，搜索也仅限这些帖子；发现模式先按标题、正文和元数据找候选，再按需使用语义检索。仅从讨论类资料中选择；实际采用哪种检索方式和覆盖范围应可见。搜索命中只是候选，不是已读证据。
3. **补读原文。** 按问题读取首帖、命中回复、相关前后楼层及后续更正。较短讨论可完整读取；长期大帖按问题和时间窗口分段。保留 TID/PID、作者、发表时间和实际读取范围；超限时说明已读与未读部分。
4. **生成结果。** 回答区分原帖说法、回复者意见、后续修正和助手推断。推荐整理提供理由与帖子来源；存在分歧就展示分歧；材料不足就明确缺口。引用必须指向本次实际读取的材料。
5. **执行与保存。** 用户要求归档、更新、导出时创建现有后台 Job；创建回执只表示已提交。用户要求保存资料集或整理时写入明确的成果版本；这属于内部保存，不由模型自行宣称成功。长 Job 交由任务卡跟踪，再决定何时继续分析。

## 目标能力集

| 能力 | 用户能做什么 | 设计要求 |
|---|---|---|
| 发现讨论 | 按作品、口味、问题、板块和时间找相关帖子 | 只在约定的讨论范围找候选，显示实际采用的检索方式；本地副本缺失不构成重建实际索引的依据。 |
| 阅读讨论 | 让助手读指定帖或搜索命中的回复，补看上下文 | 分段、有界阅读，记录实际来源位置和未读范围。 |
| 对比与回答 | 汇总推荐理由、回答具体问题、指出不同意见与更正 | 回答带可打开的原回复来源，区分讨论观点与助手推断。 |
| 昨日讨论日报 | 设置板块和生成时间；每天查看昨日热门、关键回复与历史日报 | 调度器持有规则；每天按当地日期统计候选、阅读重点、保存带来源的报告和状态。详见补充方案。 |
| 归档和导出 | 通过自然语言指定讨论或从日报选帖，归档、更新、导出并查看状态 | 明确目标与操作计划，按授权创建后台任务；完成后校验状态和文件。 |
| 整理成果 | 将一组帖子保存为资料集；按需保存带来源的笔记/清单 | 区分日报、资料集、笔记和原始帖子导出，保留来源与版本。 |
| 会话续作 | 从已选讨论、某期日报或资料集继续提问 | 固定本次资料范围，变更范围进入新的请求，不能把历史回答当成原文证据。 |

首版**不向讨论助手开放**通用 Shell、任意 SQL、任意网页抓取、批量索引管理、小说专用更新工具。日报作为有范围、有日期、有预算的受控能力接入；索引建设留在维护入口。未来的邮件能力应有独立授权、幂等键、执行回执和结果查询，不能只靠在提示词里增加指令。

## 工具边界

对模型展示少量业务语义清楚的能力，底层继续复用 application 层，不直接暴露全部公共 MCP 工具：

| Agent 能力 | 建议输入与输出 | 宿主强制规则 |
|---|---|---|
| `find_discussions` | 问题、限定板块/日期、候选上限 → 帖子候选、命中回复、采用的检索方式 | 固定 `content_kind=discussion`；范围先过滤再排序；仅返回候选标识，不伪装已读。可组合现有检索实现。 |
| `read_discussion` | TID、PID 或相关窗口、字节/楼层上限 → 实际内容、后续游标、读取回执 | 必须符合 Run 范围；产生由宿主签发的 evidence_id；保留已读和未读位置。 |
| `get_job_status` | Job ID → 状态、阶段、进度、错误、结果 | 只读真实 Job；模型不可自报完成。 |
| `request_archive_jobs` | 操作与明确 TID 集 → 授权计划或 Job 回执 | 复用 Policy 与幂等规则；确认范围后提交，结果未知时先查回执。 |
| `save_knowledge` | 资料集/笔记草稿、来源回执、预期版本 → 保存版本 | 校验来源属于当前范围；重复请求不创建重复版本；模型生成内容与人工编辑区分。 |

这些是**建议的业务接口名称**，不是当前已存在的函数。首版可先在现有受限 MCP 上做薄封装，不必另建编排框架。自然语言任务不需要每次都走向量：知道 TID 直接读，明确作品名优先结构化/关键词检索，模糊偏好再尝试语义检索。RAG 的实际含义是“检索资料、读取上下文、据此回答”，向量只是其中一种找候选的方法。

## 必须呈现给用户的状态

助手在运行中依次显示“已接收需求”“正在找讨论”“正在阅读 N 篇 / N 条回复”“正在整理回答”；只有任务系统有真实进度时才显示百分比。搜索无结果、实际检索不可用、证据不足、已达到阅读预算分别给出不同结果。停止 Run 后保留已创建 Job 的独立状态。

完成的最小结果包括：回答或任务回执、实际使用的帖子/回复、未读范围、检索方式及限制、可执行的下一步。对“找到了 10 篇、只读了 3 篇”的情况，页面不能暗示已综合全部 10 篇。

## 首版验收样例

1. “找灵异百合推荐，排除我已经知道的两部”：返回讨论候选和推荐理由，区分发帖者需求与回复者推荐；每条理由能打开来源回复。
2. “这个作品的作者归属大家怎么讨论”：同时呈现初始说法和后续更正，不能只引用首帖得出定论。
3. “只分析这 3 篇帖子”：搜索、原文、历史文件等入口都不能带入第 4 篇；更换范围须创建新的冻结 Run。
4. “把这篇讨论归档后再总结”：显示授权范围、创建 Job 回执和真实执行状态；未完成前不输出“归档完成”。
5. 无可用向量时，已知帖子和关键词路径仍可工作；实际能力不可用时说明是检索受限，不把“未找到”说成“没有讨论”。

验证中应分别检查模型输出质量、宿主边界、页面状态和 Job 完成事实。本地副本可作为结构样例；实际环境覆盖率、时效性与性能需在对应环境验证。
