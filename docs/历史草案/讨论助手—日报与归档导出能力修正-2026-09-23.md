# 讨论助手：日报与归档导出能力修正

日期：2026-09-23。范围仅讨论类帖子。本文件修正[对话—知识库改造方案](../对话—知识库改造方案.md)与[讨论助手 Agent 设计与能力集](../讨论助手 Agent 设计与能力集.md)中将定时日报推迟的判断。本文评价的是**目标产品设计**；现有代码是旧方案的实现，不能用“当前工具已开放什么”限制目标能力。本地离线帖子只用于检验内容形态，不用于判断实际部署的资料完整度或新鲜度。

## 结论与优先级

助手应有三条同级主链路：**查讨论并回答、每天生成昨日讨论日报、按用户要求归档/导出**。知识库展示可追溯的讨论和日报；对话负责设置日报规则、追问日报内容、发起归档/导出和解释执行结果。研究笔记、语义检索增强、邮件投递和通用插件体系可以随后发展。

原方案虽然提到了归档与导出，却主要围绕“研究资料→回答→保存笔记”，并把定时日报留到后面。这样不足以覆盖用户已明确的主要用途。首个完整可用版本应同时提供三条独立闭环：用户提问得到有来源的回答；配置后每天自动得到昨日讨论日报；用户委托后得到真实归档/导出结果。邮件发送不是生成日报的前提。

三类委托共用一个助手入口，但各自有明确任务契约：**范围、触发条件、输出、是否需要授权、如何判断完成**。日报由时间触发，归档/导出由用户触发，讨论问答可由用户即时触发或从某期日报继续。Agent 可以理解自然语言和组织报告，但不能靠保留一段聊天来代替长期任务状态。

## 日报要回答什么

用户说“每天早上给我昨天论坛板块热门信息”时，系统应先把规则保存为明确配置：所选讨论板块、生成时间和时区、统计日、栏目、条目上限、热点排序版本。默认的“昨天”按 Asia/Shanghai 的自然日，即当地 00:00 至次日 00:00 的左闭右开区间。使用**回复发表时间**判断当天活跃：一个旧帖昨天有新回复，应该进入昨日候选；不能按帖子创建日期排除。

建议每期栏目：

1. 昨日概况：新讨论数、回复数、活跃讨论数，均说明统计口径。
2. 热门讨论：分别展示“讨论活跃”和“值得看”，每条含标题、昨天发生了什么、当日回复/参与人数、原帖与关键回复链接。
3. 新话题与旧帖回升：区分昨天新发的帖子与旧帖昨天重新活跃。
4. 需要留意：活动模板刷屏、外链资源、意见冲突或后续更正，按实际出现情况展示，不强制填满。
5. 数据说明：本期使用了哪些板块、归档检查到何时、是否只有部分资料可用。未验证线上是否完整时不宣称“全论坛昨日全部热门”。

“热门”不是一个无解释的模型判断。先用可复核数据产生候选：当天不同回复者、有效回复数、当天新增回复、新主题等；再读取少量候选内容，剔除灌水/重复模板，整理有信息量的摘要。活跃排名与编辑推荐分别标注。建议展示排序理由，不把篇幅、累计楼层数或跨年总回复数直接当成昨日热度。

本地讨论样本揭示三种需要处理的形态：[2025 年预测活动](../../data/threads/564265/metadata.json)包含大量重复填表，单纯按回复数量可能压过有价值讨论；[长期人物讨论](../../data/threads/122509/metadata.json)跨多年，日报只能评价当天窗口，不能以整个帖子累计内容代表昨天；[《少女的港湾》讨论](../../data/threads/573256/metadata.json)有后续纠正，摘要要读回复链。这些是**内容形态样例**，不是实际部署昨日的数据，也不证明线上有上述质量问题。

## 日报执行链

```text
用户创建规则 → 保存 schedule_id、时区/板块/栏目/预算
每日调度器计算目标日 → 同一规则和日期至多创建一次日报 Job
Job 检查数据就绪情况 → 统计昨日候选 → 读取代表性回复
生成结构化日报与可阅读正文 → 保存版本、来源和运行回执
知识库“日报”列表显示结果 → 对话可基于某一期继续追问
```

调度器负责时间、去重、重启补跑和重试；Agent 负责解释用户给出的规则、从候选中归纳内容、回答追问。运行中的 Agent 不应一直等待到第二天。规则修改产生新版本，历史日报仍指向当时的规则、日期与来源。幂等键可按 `(schedule_id, target_day, rule_revision)` 建立；失败重试先查同一 Job 状态，不另造一份日报。

报告应区分“按时生成”“资料尚未就绪”“只有部分资料”“生成失败”。可设置截止等待时间；到时生成带范围说明的部分日报或明确失败，避免悄悄跳过。迟到归档若需要补报，应产生新版本，保留旧版和变化说明。是否需要远端补抓由单独同步策略决定，不让日报任务自行无限制归档。

## 原方案哪些地方要改

| 原方案重心 | 修正后的产品决定 |
|---|---|
| 助手主要做讨论研究和笔记 | 助手有三类同级任务：问答、定时日报、用户委托的归档/导出。笔记是可选成果。 |
| 日报、定时规则放在后期 | 每日规则、自动生成、历史报告和失败恢复进入首个完整版本。 |
| “生成报告”可沿用趋势报表的概念 | 日报要选出昨日具体讨论，说明热门依据、当天发生的内容和关键回复；聚合数字只是其中一栏。 |
| 知识库默认笔记首页 | 知识库优先展示讨论发现、最新/历史日报和我的整理，日报可从这里继续追问。 |
| 归档/导出只作为工具调用 | 它是完整任务链：自然语言解析对象→展示计划→授权→执行→核验→提供文件或失败处理。 |

能力集不应由现有工具名称直接决定。对模型暴露“查找讨论”“读取讨论”“生成某日简报”“提出归档/导出计划”“读取任务结果”等业务动作；调度、数据检查、授权、执行、去重和保存由程序承担。导出原始帖子、导出日报文件、导出用户整理是不同输出，界面和任务类型应区分。

## 归档和导出的对话流程

示例：“把昨天动漫区那篇讨论《某作品》的帖子归档并导出。”Agent 先找候选；若匹配到多篇，展示标题、帖子 ID 和日期让用户选定。确定目标后，系统形成归档计划并请求一次明确授权，完成归档且确认可导出后，再执行导出。页面分别展示归档与导出的任务卡和最终文件。任一步失败时停止后续依赖步骤，并保留已完成的事实。

如果用户已给出准确帖子 ID、从列表选好了帖子，或明确说“把这期日报前三篇归档”，系统可以据此形成确定的目标集合。批量操作展示完整目标集合后再执行；模型不得把“这类帖子”自行扩成所有候选并写入。导出如果需要先同步或补齐资料，要在计划中说明。只有任务成功且文件存在后才提供下载。

用户说“导出日报”时，导出的是日报成果及引用清单；“导出帖子”是一个或多个原始归档包，两者使用不同的操作名称和结果卡。初期先实现单帖/明确多帖的现有 Job 流程，资料集打包导出在具体格式确定后增加。

## 改造顺序

1. 把自然语言归档/导出的对象选择、计划、授权、任务进度和下载做成完整任务链；同时让对话提交和后台执行都有明确反馈。
2. 做“手动生成某日讨论日报”：验证时间窗、热门候选、内容摘要、来源和报告历史。用旧帖新回复和活动模板样例验收内容选择。
3. 加入每日规则和自动生成：日期去重、重启补跑、资料未就绪、失败恢复和部分结果提示；对话支持“每天生成这几个板块的日报”“暂停日报”。至此三条主链路形成首个完整版本。
4. 继续完善资料集与可选笔记。语义检索、邮件发送及其他扩展根据真实使用需求决定。

本文件是目标产品方案的修正，离线帖子仅提供内容形态样例；没有配置定时任务、运行日报、创建归档/导出任务或修改数据库。
