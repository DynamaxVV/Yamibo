# 对话—知识库分步实施与验证细则

日期：2026-09-24。状态：实施批次与验收检查清单；当前代码状态见[实现指南](对话与知识库改造实现指南.md)。本文细化[产品总纲](对话—知识库改造方案.md)、[实施架构](对话—知识库实施架构与任务拆解.md)和[Agent 选型](对话—知识库%20Agent%20选型与部署决策.md)。首版只处理讨论类帖子；本地 `data/threads` 的缺失不推断线上数据质量。开发验证通道描述的是本机 OpenAI 兼容接口；正式部署仍由 Pydantic AI 对接可配置的模型 API。凭证只从环境注入，不写入本文。

本文中的批次状态、`旧代码目前` 等现状描述冻结于 2026-09-24 规划时点；实施后发生的代码变化以实现指南和对应运行记录为准。

## 1. 三种验证层级

| 通道 | 用途 | 可以证明 | 不能证明 |
|---|---|---|---|
| 确定性 `FunctionModel`／假 HTTP 服务 | 每次提交和 CI 的快速回归、失败注入 | 工具参数、范围、幂等、事务、状态投影、SSE 回放 | 模型是否会理解真实讨论 |
| 本机 OpenAI 兼容接口 | 开发机上的真实模型语义和协议验收 | 当前端点的 Pydantic AI 工具循环、中文讨论处理、流式行为 | 其它生产端点与 NAS 网络的表现 |
| 正式部署端点 | 最终容器内验收 | 实际可达性、错误处理、延迟与运行预算 | 未检查资料的内容覆盖 |

本机模型直接走现有 `AsyncOpenAI` → `OpenAIProvider` → `OpenAIChatModel` → Pydantic AI `Agent` 路径，无需编写 Codex CLI 桥接。[当前模型创建](../src/yamibo_mcp/services/embedded_chat/runtime.py#L525)。测试进程注入 `YAMIBO_LLM_BASE_URL=http://127.0.0.1:8317/v1`、`YAMIBO_LLM_MODEL=gemini-3.8-flash-high` 和仅在本机环境中持有的 `YAMIBO_LLM_API_KEY`。不要把凭证放进配置文件、命令输出、测试快照或文档。开发机的 `127.0.0.1` 不等于 NAS 容器的 `127.0.0.1`。

2026-09-25 的最小探针已确认：鉴权后的 `/v1/models` 返回 HTTP 200 并包含目标模型；一次无副作用工具请求返回 `tool_calls`。当前 Pydantic AI 1.107.5 的最小只读工具→工具结果→中文最终回复也已通过；接下来仍须在项目 MCP 路径上测多轮操作，另测 stream、超时、401／429／5xx、取消和并发。记录端点类型、模型、框架版本、请求状态与实际回执，绝不记录凭证或长段私有原文。

## 2. 批次 0：先固定运行边界与可复验基线

**实现拆分。** 保持现有 Pydantic AI `Agent`、Run／SSE 存储和受限 MCP；现有 `service.model` 注入继续用于确定性测试。真实模型测试直接使用当前 OpenAI 兼容 provider，避免测试专用模型桥接。单独把 Pydantic AI v1 锁定维护补丁并回归，不把 v2 迁移、Hermes 切换、业务新表混为一次修改。[当前依赖](../pyproject.toml#L17)、[运行器](../src/yamibo_mcp/services/embedded_chat/runtime.py#L487)。

**先决试验。** 模型目录及单次工具调用的探针已通过；下一步在隔离测试库验证 Pydantic AI 的“最终答复→只读工具→工具结果后答复”完整循环，并核对流式事件与失败行为。另在隔离 PostgreSQL 上测长帖、更正、两字关键词、板块／日期过滤的执行计划与延迟；核对旧 Hermes 会话、实际 NAS Compose 配置和 `linux/arm64` 镜像。临时测试库不指向当前有价值的本地或生产数据库。

**出口。** 写下可复现的脱敏模型测试方式、端点／模型结果、检索预算与索引选择、ARM64 依赖结果及未知项。端点探针通过不等于完整 Agent 验收；若多轮工具流失败，阻止宣称语义验收。生产 API 尚未选定时，生产协议验收保持未完成。

## 3. 批次 1A：讨论发现、冻结范围与可核对引用

**服务与数据。** 新建原文发现查询，先以论坛分类及 `content_kind` 限定讨论，再在标题和实际原文楼层中找候选；旧 `rag_chunks` 只作可选增强，不成为必经路径。短中文词检索根据批次 0 的 PostgreSQL 测量选索引，查询始终有范围、上限和超时。返回 `actual_mode`、TID、命中 PID、候选理由；候选结果不是“已读”。[现有 RAG 门控](../src/yamibo_mcp/application/rag_queries.py#L19)、[原帖读取](../src/yamibo_mcp/application/archive_queries.py#L33)。

**读取契约。** `DiscussionScope` 由服务端签发并冻结会话、模式、板块／时间、选定 TID/PID、报告版本和所有者。工具和 Web API 同调应用服务，逐次取授权交集。按 TID/PID、内容哈希／版本、段落范围读取，产生 `SourceReceipt`；原帖变化或游标失效要明确提示，不让 offset 跳页造成伪完整。回答引用只能指向本 Run 真正读取的回执。统计回执独立于原文回执。

**边界用例。** 指定三帖不能检索、读取或引用第四帖；旧帖昨日新回复可被目标日找到；无命中、索引未就绪、读取超预算、源内容变化、非讨论帖、被截断长帖分别有稳定状态。隔离 PostgreSQL 集成测试检查过滤先于 Top K、并发新增楼层及实际 PID。离线缺帖只使相应用例“不覆盖”，不当作生产缺失。

**出口。** 关闭 Embedding/RAG 时，限定范围的原文发现与有界阅读仍可用；任一展示引用可回到确切 TID/PID 和片段。

## 4. 批次 1B：助手与知识库界面接上同一范围／成果

**Run。** `POST /api/chat/sessions/{id}/runs` 增加模式、冻结范围和可选报告版本。幂等指纹覆盖规范化输入与所有范围字段，同一 `client_request_id` 改范围返回 409；旧代码目前只比较 input。[现有逻辑](../src/yamibo_mcp/services/embedded_chat/runtime.py#L230)。模型只能使用按 Run 范围裁剪的发现／读取工具，来源回执校验在应用服务，不在提示词。

**助手 UI。** 点击即显示“正在提交”的本地用户消息；服务端接受后转“排队／检索／阅读／等待授权／后台执行／完成或失败”。提交失败保留输入及原 request ID 可重试。连接状态与业务阶段分开；Run 结束后 Job 卡继续独立更新。模型文字不能改变卡片状态。对话引用点开原帖准确楼层。

**知识库 UI。** `/rag` 保留兼容入口，首页显示讨论搜索、最近／历史日报及资料检查情况；原索引维护移二级入口。讨论详情和日报详情能把服务端 scope／report ID 带进助手，不能靠复制标题或自然语言重新猜对象。旧 API 不静默改变响应。

**验证。** 确定性模型先测 401、409、空结果、断线重放、重复提交和长任务时另发短问答；本机模型端点通过多轮契约后，以真实讨论问题测“发现→补读→引用”及更正识别。模型答对不代替人工核验引文含义；前端修改须运行 `cd c && npm run build` 并在浏览器检查窄屏与任务重开。

## 5. 批次 2：冻结归档／导出计划，交给固定 Job 链

**对象。** `operation_plan` 保存目标 TID、每帖步骤、格式、成本上限、批准摘要和版本；`operation_item` 保存每帖归档、必要的 full 升级、导出、文件校验状态。自然语言只帮助提出候选与草案；对象不确定时停在候选选择，批准由独立 API 验证计划摘要与所有者。已批准计划不允许模型扩大目标或增加步骤。

**推进。** 批准后应用服务创建 Job，Daemon 只按计划状态机推进。沿用现有受限工具对 Job 与操作回执的同事务模式，而非另建一套不明提交边界：[受限工具](../src/yamibo_mcp/services/embedded_chat/mcp.py#L188)、[借用连接](../src/yamibo_mcp/db/transaction_scope.py#L4)、[原子回执测试](../tests/unit/test_embedded_chat/test_runtime.py#L152)。新后继阶段也须“阶段状态＋后继 Job”同事务并用唯一阶段键，重启后先查实际 Job 和文件，再决定续作。`capture_mode=text_only` 不能直接导出需要图片的成品，升级步骤必须出现在计划里。

**边界。** 同一批准并发或重放仅执行一次；模型超时不重提计划；单帖失败不抹掉其他帖结果；归档成功而导出失败呈部分完成；文件必须有实际存在及可打开的校验；取消只停止尚未开始的阶段，已完成事实不回滚。用入队前后、写回执前后的故障注入和重启恢复测试。卡片从持久化计划／Job 快照恢复。

## 6. 批次 3：先做手动日报，再做模型编辑

**期次。** `daily_issue` 冻结板块、目标日 `Asia/Shanghai` 的 `[start,end)`、资料截止时间及规则／手动配置；`attempt` 记录重试；`report_revision` 保存不可变正文、统计回执、原文来源与缺口。手动同配置重复创建复用同一期，明确补报才新增版本。模型运行失败仍保留已经算出的事实及部分状态。

**资料。** 先按既有扫描／同步能力形成“查到哪页、何时查、是否触达目标日边界、候选同步终态”的快照。扫描预算或截止时间不足时报告 `partial`／`failed`，不能把最新回复时间当全板块完整证明。活跃榜由程序按目标日唯一 PID 和实际发表时间算；同一老帖的新回复计入目标日，历史背景只供解读。现有趋势构建和报告可借算法，但其查询没有完整讨论过滤、日报期次／版本也不是旧报告对象。[趋势构建](../src/yamibo_mcp/application/discussion_trend_builder.py#L191)、[旧报告](../src/yamibo_mcp/application/discussion_report.py#L40)。

**编辑。** Pydantic AI 只在有界候选和回执上生成“值得看”与说明；不改统计排名。输出按 schema 校验 TID/PID、目标日／背景／后续更正的时间归属、来源回执是否存在。无有效引文的推荐退回修正或标成不完整，不能伪造来源。本机模型端点通过多轮契约后用长年帖、重复活动模板和后续更正样本做语义验收；人工逐条检查“摘要是否真由引文支持”。报告可从知识库重开并带版本追问。

## 7. 批次 4：定时规则与无人值守执行

**规则。** 保存板块、时区、每天执行时点、资料准备截止、预算、启停状态和 `rule_revision`。数据库唯一键保证同一规则版本／目标日逻辑期次只创建一次；失败重试只增 attempt，修改规则不改旧期。默认创建于当天执行时点之后则次日生效；暂停期间不补跑，恢复后从下一执行点开始。非暂停的停机只补最近一个且在 48 小时内的目标日，更早的手动补报。

**调度。** Daemon scheduler 只判断到期并原子创建 issue／Job，不持有跨天模型会话；日报 Job 用批次 3 同一生成服务。并发轮询、跨午夜、服务器时区与浏览器时区不同、暂停／修改／恢复、模型超时、资料迟到、重试和补报全部以持久状态测试。启用前用时钟注入连续模拟多天，检查“恰好一期”和报告版本不被覆盖。

**出口。** 用户可在知识库看到连续期次、资料检查缺口和失败原因；在助手修改规则时看到确切的下次执行时间。此批通过后才称首版三条能力全部可用。

## 8. 最终发布门槛与明确未验收项

每批先跑纯程序单元与隔离 PostgreSQL 集成，再跑本机兼容端点的语义／协议样例，最后按变更范围做浏览器和 ARM64 真机检查。若正式部署仍使用同一服务，也要从 NAS 容器内重新验证可达性、Pydantic AI 工具调用、中文流式／重连、401／429／5xx、取消、预算与费用。此前不得把“开发机本地端点通过”写成“NAS 已验收”。不对现有本地或生产数据库运行破坏性迁移；先在隔离库演练，发布阶段再核对目标环境。
