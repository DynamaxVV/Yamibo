## 线上观察：先解决“能否进入、失败时能否理解”

| 本次观察 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 首页直接 GET 返回 HTTP 200，单次约 0.91 秒，取得前端应用入口 | 网站入口可达 | 不是模型首响应时间，也不是页面整体性能 |
| 网页文本读取取得首页显示 100367 篇帖子 | 归档规模已达十万级，至少页面当次读取如此显示 | 文本读取可能有缓存；不代表十万篇原文完整、全部可检索 |
| 对话文本页显示“未配置”和“对话服务暂不可用或尚未配置” | 当前无令牌访问的可见提示如此 | 不能据此断言服务器没配模型 |
| 直接 GET 对话上下文两次返回 401；第二次读取到 `CHAT_AUTH_REQUIRED / 需要对话访问令牌` | 本次访问缺少 Chat 所需鉴权 | 未确认授权用户能否正常对话，也未确认 embedded/Hermes |
| 知识库文本页停留在 Loading；概览接口先后在 20 秒、45 秒超时，均未收到响应正文 | 此访问路径当时无法及时取得概览 | HTTP 000 是客户端未取得状态码，不是服务器返回的错误码；不能据此断言数据库故障或索引为空 |

来源：[线上首页](https://web.dynamaxvv.me/)、[对话页](https://web.dynamaxvv.me/chat)、[知识库页](https://web.dynamaxvv.me/rag)、[对话上下文接口](https://web.dynamaxvv.me/api/chat/context)、[知识库概览接口](https://web.dynamaxvv.me/api/rag/overview)。页面文本通过 agent-reach 的 Jina Reader 获取；接口状态通过直接 GET 获取。

**证据：Chat 混淆了“无法读取配置”和“没有配置”。** [useChatSessions.ts](../c/src/hooks/useChatSessions.ts#L16) 同时等待上下文及会话列表，失败时留下错误；[Chat.tsx](../c/src/pages/Chat.tsx#L78) 把空上下文转换成 ready=false，再于第 150 行显示“未配置”。[请求客户端](../c/src/api/client.ts#L2) 从 sessionStorage 附加令牌。线上 401 与本地逻辑共同支持“未授权容易被误呈现为未配置”的判断。第一步应分开呈现加载中、需要令牌、服务不可达和确实未配置，并提供对应恢复入口。

**证据：知识库首屏受概览接口整体完成约束。** [Rag.tsx](../c/src/pages/Rag.tsx#L66) 通过 Promise.all 等待概览与分区，成功才结束 loading；失败分支只设置错误，没有结束 loading；[第 303 行](../c/src/pages/Rag.tsx#L303) 又优先返回 Loading，因此请求失败后也可能看不到错误。这是当前本地代码的确定缺口；本次线上超时与它相符，但尚未证明线上资产完全相同。

**推断：概览的同步全库统计是值得测量的瓶颈候选。** [概览路由](../src/yamibo_mcp/web_fastapi/routers/rag.py#L18) 一次请求串联概览计数、楼层覆盖诊断、任务和分区汇总；[覆盖统计](../src/yamibo_mcp/db/repositories/rag_chunks.py#L228) 涉及全量 floors 内容判空和分块去重计数。十万级帖子下，其开销值得调查，但还缺数据库查询耗时、锁等待及执行计划。正确的近期方向是让资料入口不等待所有维护统计，分别加载或使用带更新时间的统计快照；不应先以重建全部向量来处理页面 Loading。

### 对话：原讨论多数成立，但不能夸大为“完全没有状态或恢复”

- **提交反馈晚。** [Chat.tsx](../c/src/pages/Chat.tsx#L110) 先等待 run.start，再显示 pendingUser。应先显示“正在提交”，成功后显示已接收；失败保留草稿和原请求标识，避免重试重复建任务。
- **有业务状态，却不在最明显的位置。** [主区域状态逻辑](../c/src/pages/Chat.tsx#L16) 没有 queued/waiting_jobs 专门分支，但[工作面板](../c/src/components/chat/ChatLocalPanel.tsx#L6) 已有相应标签。问题是主流程表达不足，不是后端没有这些状态。
- **工具失败展示协议不一致。** [后端](../src/yamibo_mcp/services/embedded_chat/mcp.py#L131) 将失败放入 tool.completed.result.error；[工具事件组件](../c/src/components/chat/ChatToolEvent.tsx#L1) 检查顶层 error。这里会弱化实时错误展示，不意味着模型一定拿不到错误。
- **Job 进度过于粗。** [wait_for_jobs](../src/yamibo_mcp/services/embedded_chat/mcp.py#L375) 只在 status 列表变化时发 job.progress；同为 running 时的阶段与数量变化不会发出。[对话记录](../c/src/components/chat/ChatTranscript.tsx#L90) 也没有相应任务进度卡。
- **有重连，但耗尽后的恢复存在缺口。** [useChatRunStream.ts](../c/src/hooks/useChatRunStream.ts#L37) 将本地状态设成 unknown/terminal；[followRun](../c/src/hooks/useChatRunStream.ts#L117) 对同一 run_id 直接返回。已有重试、序号恢复及页面唤醒机制，不能笼统说 SSE 不可靠。耗尽后服务端仍执行的场景需独立浏览器复现。
- **等待后台任务仍占执行名额。** [调度器](../src/yamibo_mcp/services/embedded_chat/runtime.py#L384) 按尚未完成的 execute 数量限制并发；等待也计入墙钟预算。原讨论建议将长期后台等待与模型执行分开，方向合理，但持久化续作需明确触发条件、幂等和失败恢复，不能只加一个回调。

我会优先修前四项，先让“提交、接受、后台执行、实际结果”可区分。性能优化应测量后决定；换模型或增加并发都不能修复这些信息表达问题。

### 知识库：最严重的问题是“限定了范围，却没有真正限定证据”

原讨论指出 knowledge fallback 不传日期，核对后发现影响面更大：

- [常规论坛证据路径](../src/yamibo_mcp/application/discussion_trend_queries.py#L633) 调用的 RAG helper 不接收开始和结束日期；只有 [SQL fallback](../src/yamibo_mcp/application/discussion_trend_queries.py#L657) 明确传递日期。
- [knowledge 的第二层 fallback](../src/yamibo_mcp/application/knowledge_queries.py#L435) 同样只传问题及分区。
- [楼层分块](../src/yamibo_mcp/rag/chunker.py#L110) 使用帖子级 publisher/pub_time，不能直接当作该回复作者及发表时间。

这意味着，“研究 2014 年讨论”的标题、范围标签和引用列表都有了，实际证据仍可能来自其他年份；即便每条引用能打开，也不等于研究结论可信。应把日期、作者及资料范围作为检索和原文读取的共同约束，再做跨时期比较。

其他原讨论主张仍成立：

| 问题 | 当前证据 | 对产品的含义 |
|---|---|---|
| keyword 也受 rag_enabled 门控，查询 rag_chunks | [rag_queries.py](../src/yamibo_mcp/application/rag_queries.py#L34) | “无向量”和“无法找原文”需要拆开；已有按帖原文读取不应被概括为全站不可用 |
| PG 关键词按空白拆词做 ILIKE，summary/楼层/id 排序 | [rag_chunks.py](../src/yamibo_mcp/db/repositories/rag_chunks.py#L529) | 找到候选不等于最相关；需用真实中文问题检验检索质量 |
| hybrid 向量失败后仍返回原始 mode | [rag_queries.py](../src/yamibo_mcp/application/rag_queries.py#L54) | 用户与模型都应获知实际检索方式和遗漏风险 |
| indexed_threads 仅要求至少一块向量完成 | [rag_chunks.py](../src/yamibo_mcp/db/repositories/rag_chunks.py#L194) | 不是完整率或新鲜度，不能用于证明全库已准备好 |
| Chat 搜索白名单只开放 query/mode/top_k | [mcp.py](../src/yamibo_mcp/services/embedded_chat/mcp.py#L34) | 页面所选范围尚未形成稳定的工具约束 |
| PG 向量查询不按模型身份隔离 | [postgres_vectors.py](../src/yamibo_mcp/db/repositories/postgres_vectors.py#L60) | 换模型时存在同维不同空间混用风险；未证明生产已混用 |

### 两个原讨论未充分展开的复用边界

**已有纯文本演练，尚未产品化。** 当前工作树的[演练文档](知识库纯文本演练.md#L1) 与[脚本](../scripts/demo_knowledge_text_pipeline.py#L48) 已展示绕过 embedding、复用分块和真实 MCP 的连接方式。脚本明确绕过正式索引 handler，LLM 使用预设模型，活动枚举也是 SQL 探针。可以复用其验收样例和接口缺口清单，不能把它当作真实模型自主研究或线上纯文本索引已经完成。本轮没有重跑该演练，文档内历史数字也不是本次测试结果。

**已有报告持久化和工作文件版本，不等于完整成果版本链。** [报告 handler](../src/yamibo_mcp/daemon/handlers/discussion_trend_report.py#L228) 保存 JSON/Markdown，但[报告仓储](../src/yamibo_mcp/db/repositories/discussion_trends.py#L603) 对同一 run_id/report_kind 冲突会覆盖。另一方面，[工作文件](../src/yamibo_mcp/services/embedded_chat/files.py#L205) 已有 revision/hash 检查及旧内容保存。应复用这些基础，补齐“本版用了哪些材料、哪些正文由人修改、下一版如何继承”，而不是另建第三套泛化文件系统。

## 我建议的融合方式

保留页面分工，但把同一份范围、证据及成果关联起来。现有帖子列表继续负责选资料，任务中心继续负责后台任务；知识库无需再复制一套归档浏览器。

第一条路径刻意收窄为：

1. 在已有归档中选择少量明确帖子。
2. 进入助手后显示选中范围；由服务端限制工具读取范围，不只在提示词里写“不要越界”。
3. 逐页读取原文，记录实际读取的 PID/楼层、未读取部分、原文版本或内容哈希。短回复补读上下文；长帖不允许把 Top K 片段标成全文总结。
4. 给出带来源的回答；用户选择保存，保存正文及这次实际使用的证据清单。
5. 在知识库找到这份成果，打开来源或继续讨论。原文变化时保留旧版本，提示“来源已变化”，不自动认定“结论已失效”。

这里可先使用两类轻量记录：一次研究的上下文，以及一个成果版本。但“固定资料集”还应区分“固定帖子 ID”与“固定内容快照”：同一帖子会新增和编辑回复，仅保存 ID 无法复现当时依据。保存的动态查询则用于以后发现新材料，不能代替旧成果的来源快照。

第一版不必同时完成全局趋势、主题自动发现、全库增量向量和订阅提醒。先证明你会主动再次打开已有成果，才值得投入长期研究平台。邮件和定时任务依旧后置：它们负责触发和交付已有成果，不能替代资料范围与版本的正确性。

## 建议顺序与验收

| 顺序 | 改进范围 | 可核验的结果 |
|---|---|---|
| P0：入口可用 | 区分鉴权/未配置/不可达；修知识库 Loading 和错误恢复；测概览慢查询 | 无令牌明确提示访问凭据；概览慢或失败时仍能进入资料操作，看到错误和重试 |
| P1：反馈与证据可靠 | 提交气泡、工具失败、Job 阶段；日期/作者/范围/检索降级 | 工具失败可见；同状态的 Job 进度可见；限定时期的证据不会跨期；降级不冒充完整检索 |
| P2：一个知识闭环 | 选帖、原文读取、引用、保存、重新打开继续讨论 | 保存结果能够追到实际原文和读取范围；关闭再开保留关联；不依赖全库向量化 |
| P3：按真实使用扩展 | 耗时治理、长任务续作、来源变化提示和有预算的增量索引 | 查询不被长期等待挤占；更新不覆盖人工修改；新增材料及处理费用可解释 |

不要将以上直接理解成已经批准的实现计划；本次交付是分析。技术方案仍需依据实际最常用的研究问题及生产查询剖析确定。

## 本次验证与尚未解决的问题

执行了知识研究查询与 embedded runtime 两个现有测试文件：**29 passed，1 skipped，14 warnings，7.16 秒**。警告涉及 MCP/Agent 流及 FastAPI 生命周期弃用。测试没有证明生产性能、真实模型规划或视觉体验，也没有覆盖本文指出的日期越界及 UI 失败恢复场景；不应因全部已执行测试通过而忽略这些缺口。

原文记录额外按四条消息逐条核对，确认没有删改原消息文本。未修改前端代码，因此没有重新构建静态资产。

仍未知：生产后端模式和部署版本、授权后的首反馈耗时、概览超时的具体耗时点、生产文本/向量实际覆盖与新鲜度，以及用户最值得反复使用的研究场景。本次网页文本足以指出入口问题，不足以评价间距、视觉层级、移动端布局等细节。

下一次有意义的检查是：在已授权访问下采集一次只读查询的接收/排队/首工具/首回复时间线，并取得知识库概览内部各查询耗时。它们分别用来定位“助手慢在哪里”和“为什么知识库进不去”；本次没有为此索取或绕过访问令牌。
