# 讨论助手：日报与归档导出任务契约

日期：2026-09-24。本文是[现行总纲](对话—知识库改造方案.md)的后台任务专项；验收目标和阶段以总纲为准。[旧版](历史草案/讨论助手—日报与归档导出能力修正-2026-09-23.md)保留作历史记录。本地离线帖子仅为内容形态样例，不说明服务器近期资料是否齐全。

## 1. 昨日讨论日报是什么

用户设置板块、每天执行时间、默认时区 Asia/Shanghai、栏目与条目上限。每期以一个目标日为准，时间窗为该日当地 00:00 至下一日 00:00，左闭右开。昨天有新回复的旧帖也进入候选；帖子创建日不决定其昨日热度。

日报固定区分两类内容：

| 栏目 | 依据 | 呈现 |
|---|---|---|
| 昨日概况、讨论活跃 | 程序按目标日实际可用回复计算：新讨论、不同活跃讨论、回复和参与人数 | 展示统计口径、已检查范围与统计回执，不由模型改写排名 |
| 值得看与内容摘要 | 有界读取当日关键回复以及必要背景，模型归纳信息量、争议和更正 | 每条有推荐理由、原帖与关键回复引用；可与活跃榜不同序 |

重复活动模板不能只因回复多占满“值得看”；跨年长帖只统计昨日活动，不能拿累计楼层充当昨日热度。[活动帖](../data/threads/564265/metadata.json)、[长年讨论](../data/threads/122509/metadata.json)、[含后续更正的讨论](../data/threads/573256/metadata.json)仅用于验收这三种内容形态，不代表线上昨日情况。

统计严格限于目标日的发表时间，按唯一回复 ID 去重；新讨论、回复和参与人数分别标明是否计入首帖与缺失时间的回复。重复模板可影响“值得看”选择，但不悄悄改变原始回复数。为理解昨天的回复，允许有界阅读同一讨论的更早楼层，标为背景且不增加当日数字；生成前已出现的目标日后更正单列“后续补充”及实际时间。统计引用聚合回执，内容叙述引用已读取的原回复。报告保存结构化栏目、正文、口径、引用片段、已读清单、数据状态及生成时间；不依赖研究笔记编辑系统。

## 2. 昨日资料从哪里来

产品承诺“指定板块昨天的主要讨论”需要一个**有界的近期资料准备流程**，不能只凭大量历史归档。日报规则绑定哪些板块、由哪个归档同步流程准备近期帖子、预计何时完成和检查截止时间。建议该流程先扫描指定板块按最近回复排序的论坛列表，记录实际检查的页、列表快照与时间区间；尝试扫到活动时间早于目标日的边界，再对候选 TID 做受控同步，已有归档也要检查昨天新增回复。达到页数或时间预算而尚未扫到边界时，记录未检查范围并按部分资料处理。具体论坛分页与更新能力在实施时验证，不将一个旧帖的最新回复时间当成完整覆盖证明。

每期生成前读取准备流程的检查记录：检查覆盖了哪些板块、页／时间范围，候选中哪些同步成功、失败、仍运行，最近完成时间是什么。已发现候选全部处理到终态且检查范围满足规则时，才开始正常报告；否则等待到截止时间。页面展示这些**已检查事实**，不把“看见昨天最后一条回复”当成“昨天全部回复都已同步”。检查记录不足或到截止时间仍有未完成项，按规则交付标明范围的部分日报或报失败；不以未核实的覆盖生成看似完整的全板块结论。日报 Job 不自行进行无界远端补抓。

同步和生成分开：同步流程可以按周期准备资料；日报调度器只在有足够的已检查范围、或已到明确截止时间时进入候选计算。未完成时显示“等待资料”及下次检查时间，失败和部分结果可从知识库进入。真实部署的同步安排与覆盖状态需在实施前按对应环境验证，不能依据本地离线副本判断。

## 3. 调度、期次与版本

四个对象各司其职：

| 对象 | 身份与状态 |
|---|---|
| 每日规则 | schedule_id、板块、时间、时区、栏目、预算、是否启用、rule_revision |
| 逻辑期次 | (schedule_id, target_day) 唯一；首次创建时冻结规则版本和资料准备要求 |
| 执行尝试 | 同一期的 Job 与重试回执；失败重试不创建新逻辑期次 |
| 报告版本 | 同一期首次报告与明确补报；迟到资料或用户重新生成时新增版本并记原因 |

规则当天在执行时间之后创建，默认从下一个执行日开始；用户可单独手动生成指定日期。暂停期间不产生期次；恢复后从下一执行时间开始，不自动补暂停期。非暂停的服务停机恢复后，自动补跑最多最近一个遗漏目标日，并设置有限时间窗（建议 48 小时）；更早日期留给用户手动补报，避免突然批量调用模型。以上是默认产品语义，UI 设置页应明确展示。已创建期次不会因规则修改自动换用新版本。

手动生成某日也应有期次或等价的请求身份，重复提交返回相同任务；明确“重新生成”才产生同一期新报告版本。报告版本不可被后续自动任务静默覆盖。生成失败保留期次和原因；重新执行先核查原 Job 状态与已保存报告。

## 4. 归档／导出完整委托

用户可以给准确 TID、选中讨论，或从某期日报选择条目。候选可来自本地讨论元数据或受限论坛列表预览；不开放任意网页抓取。若说“这期日报前三篇”，必须绑定 report_id、report_revision、栏目、顺序和最终 TID；两个栏目同时存在而上下文未指定时，请用户选栏目。计划展示标题、目标 TID、预期操作、是否允许更新／补齐、导出类型、成本边界与逐帖处理策略。用户确认时授权整个计划。

固定任务链为：确定对象与当前归档状态 → 必要时归档／更新／补齐 → 核实准备结果 → 导出 → 核实文件并交付。它是持久化业务任务，不靠聊天 Run 长时间等待。计划至少保存 plan_id、冻结 TID 集、来源（页面选择或日报版本）、授权记录、每个 TID 的阶段和 Job ID、成果引用、失败原因与更新时间。重启后按回执继续，不盲目重新提交。

默认逐帖处理依赖：A 帖归档失败时不导出 A；B 帖成功则继续导出 B，最终汇总完整、部分完成和未执行。用户明确要求“全部成功才交付”时采用整体约束。第一次展示计划时说明策略。每个阶段创建 Job 后展示回执，Job 完成且结果可用才进入下一阶段。结果未知先查旧回执和文件，不以重试制造重复操作。

“导出原帖包”“导出日报”“导出用户整理”分别命名和交付。单帖与明确的多帖逐项导出进入首版；把多个原帖打成一个新格式的资料集包可后置。导出若隐含远端同步，应在完整计划中可见，不能让一句“导出”静默扩成无界抓取。

固定“归档后导出”由首版后台自动衔接；普通“归档完成后再做一项开放式研究”若无持久化续作，应显示回执并由用户发起后续请求。两者在界面上明确区分。

## 5. 跨页体验和状态

知识库首页显示最近日报、讨论搜索及需要处理的资料缺口；日报详情展示范围、版本、统计与原文两类来源、“问助手”和“选帖处理”。用户继续问某一期时绑定报告版本与来源；要求“后来怎样”须新建时间范围，不能把新内容写进历史日报。助手页可创建、修改、暂停日报规则，展示下次生成时间和最近一次执行状态；可从日报卡发起归档／导出计划。

一个日报 Job、归档阶段 Job 或导出阶段 Job 正在运行时，用户仍可发起简短查找／问答。关闭页面后状态仍可找回。停止聊天只停止后续推理；已持久化的日报规则和已授权的操作计划需有各自明确的暂停／取消入口及真实状态。

## 6. 最小可验收场景

1. 昨天老帖新回复入候选，背景旧楼层只用于理解，后一天更正单列；时间和时区显示正确。
2. 活动模板大量重复：活跃统计依口径展示，模型可不将其列入“值得看”，不能篡改统计排名。
3. 同一规则同一天自动只建一个逻辑期次；当天改规则、失败重试和手动补报分别表现为冻结配置、执行尝试和报告新版本。
4. 近期同步只检查部分板块页面：日报显式标明已检查范围和部分状态，不宣称全板块完整。
5. 从日报某栏目选两帖，授权完整“归档后导出”计划；中途关闭页面或重启仍能完成，失败一帖不阻断成功帖。
6. 长任务执行中短问答仍能完成；任务卡阶段变化和真实文件可用状态一致。
