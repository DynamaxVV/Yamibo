# 讨论类真实数据复核：对话与知识库方案修正

日期：2026-09-23。范围按用户最新要求，仅考虑讨论类帖子。本文是数据分析与方案评价，不是实现或数据库修复记录。

> 样本边界：用户已说明本地离线副本存在正常缺失。本地文件数量、数据库状态、索引覆盖及同步时间只描述本次副本，不能外推实际部署的完整性、时效性或检索质量。产品判断依据讨论内容及交流结构，不以本地缺口作为改造前提。

## 结论

原方案的“有范围、有进度、有来源、可继续”仍成立，但“知识库默认笔记首页”“首版主要让用户先选帖子”“正文检索后置”需要调整。

建议改为：**知识库先承担发现讨论、筛选讨论、收集相关帖子；助手负责从这些讨论中查找、阅读、比较、解释。笔记是可选成果。**

讨论检索应是核心能力，因为用户往往知道想问什么，却不知道相关帖子在哪里。实际环境是否需要补建索引，应另行验证，本地副本不能提供这一结论。传统关键词检索后读取相关上下文，也属于广义的检索增强回答；此前“不需要 RAG”应准确表述为“不要求先完成全量 Embedding”。

## 1. 证据范围与方法

- 实际连接本机 PostgreSQL 127.0.0.1:5432/yamibo，public schema；连接参数强制 default_transaction_read_only=on，并核实 transaction_read_only=on。直接 SQL 聚合，无应用初始化、迁移、索引、模型调用或远端访问。
- 数据库统计限定 threads.content_kind='discussion'，对应动漫区和海域区。该标签按现存数据统计，不等于每个帖子的内容都是普通议论。
- 文件扫描 data/threads 下全部 metadata.json，确定分区及与数据库的交集后，只将两个讨论分区用于本次结论。metadata 没有顶层 content_kind，分区取 context_inputs.forum_id，另与 context.md 的 board 字段核对。
- 按短交流、推荐求助、作品问答、长期讨论、模板活动分层抽读；没有把少量内容样本称为随机代表性调查。
- PostgreSQL 与离线文件不是完全相同的快照，分别报告数量。原文长度包括引用、表情代码和可能残留的页面文本，不等于净信息量或模型 token 数。
- 报告中的样本观点只用于理解讨论结构，不采纳为外部事实。例如《少女的港湾》的作者争论，本次只观察论坛如何提出与纠正观点，没有核实作品史实。

## 3. 本地索引快照（不用于判断实际项目覆盖）

| 讨论类索引指标 | 实测 |
|---|---:|
| 有任意 rag_chunks 的帖子 | 9,173，占讨论帖 20.72% |
| 分块数 | 318,803 |
| 分块关联的不同 PID 数 | 298,611，约为讨论楼层数 19.98% |
| 索引覆盖帖中创建于 2004—2007 年 | 9,165，占 99.91% |
| 分块 indexed_at 范围 | 2026-06-23 至 2026-06-28（UTC） |

这里的“关联 PID 占比”不等于语义完整覆盖率；同一楼层可能只索引部分文字。分区分别覆盖：动漫区 7,107 篇、海域区 2,058 篇，合计 9,165；按当前 threads 关联统计得到 9,173，说明分块自身 forum_id 与当前帖子分类也不能混为一套口径，正式覆盖诊断应统一以当前范围定义计算。

状态分布为 indexed 311,784 块、completed 2,848 块、failed 4,171 块。前两类都有非空向量，失败类没有。当前向量查询按非空 embedding 过滤，而概览按 indexed 计数，因此“存在向量”“状态计入概览”“可用且最新”需要区分，不能把 completed 一概当成没有向量。[查询实现](../src/yamibo_mcp/db/repositories/postgres_vectors.py#L73)。

对两个讨论主题做相同字面词的只读核对：

| 关键词 | 当前讨论标题或原楼层命中的不同 TID | 旧分块正文/标题/元数据命中的不同 TID | 两者交集 |
|---|---:|---:|---:|
| 星灵感应 | 75 | 0 | 0 |
| 少女革命 | 758 | 227 | 227 |

方法：原始候选为标题命中与楼层 content 命中的 TID 并集；索引候选为分块 text/title/metadata_text 命中的 TID，均以当前 thread 的 discussion 标签约束。使用 ILIKE 子串条件，没有调用 Embedding。数字只证明字面候选覆盖差距，不代表相关性评测、语义召回率或生产搜索耗时。

**边界：**以上仅说明本地原文与索引副本覆盖不同，不证明实际项目存在相同差距，也不构成重建索引的依据。讨论检索进入首版，是因为推荐求助和作品问答需要发现相关讨论。优先复用并验证现有检索能力，再决定是否改进。

这些样本支持“找讨论、看意见、整理推荐、回答具体问题”，还不足以证明“频繁生产长研究报告”是核心需要。因此知识库首页应先是讨论探索和人工资料集，笔记放在同页的“我的整理”中。

用户限定讨论类后，不规划漫画阅读、小说章节管理或 OCR 产品能力。但讨论标签中确实混入发布说明、长篇搬运和活动模板；应按内容角色提示或过滤，不能仅凭 forum_id/content_kind 把全部正文当成讨论意见。

## 5. 附带本地观察（不作为产品改造前提）

以下异常仅在本地样本验证，不证明实际部署存在同样问题。代码分析说明特定输入条件下的风险；是否影响实际项目应另行核实，不据此要求生产修复或重建。

### 本地样本与条件性代码风险：重复显示楼层号

PG 全库 floor_no 重复组涉及 10,067 帖；这些都在讨论范围对应的动漫区核对路径中发现，离线文件发现 9,901 篇重复 floor_no 帖，全部位于动漫区。重复显示编号不等于重复 PID，也不能直接去重删除回复。

[538461 metadata](../data/threads/538461/metadata.json#L32) 有 188 个不同 PID，但只有 20 个不同楼层号。首帖 PID 40785923 是发布说明；[context.md](../data/threads/538461/context.md#L21) 却在原作者标题下使用另一位回复者 PID 41447907 的评论。该帖 PG 与 metadata 按 PID 核对，187/188 条正文完全一致，另一条差一个字符；不能笼统说原始 PG 也错了。

原因可在 [thread_context.py](../src/yamibo_mcp/application/thread_context.py#L42) 确认：先以 floor_no 建字典，再按该键回填正文，同号内容覆盖。65176、108718、122509 的 context 也有抽样正文坍缩证据；尚未审计全部受影响 context。

原文 API 直接读 PG，不走上述 context 回填；但按 floor_no 精确跳转仍有歧义。[原文读取](../src/yamibo_mcp/application/archive_queries.py#L95)。

**设计建议：**引用使用 tid+pid 标识回复，floor_no 用于展示。本地 context 错配应单独评估，不列为页面改造先决条件，也不据此要求实际项目重建数据。

### 需要纠正前次结论：代码风险没有在本地现存分块中普遍出现

对全部现存可关联原楼层的 321,158 条分块核对，publisher 和 pub_time 与对应原楼层的不一致数均为 0。这个统计含非讨论分块，是补充的数据质量核验，不用于讨论规模统计。

因此，“某代码入口可能写入帖子级时间”仍是需要测试的风险，但不能说本地现有 RAG 已普遍误写作者日期。context 错配、重复楼层号、研究日期过滤缺失和分块元数据问题是不同边界。

### 直接读原文也需要有界分段

普通短帖适合完整读取，但 discussion 标签内存在单楼层超过 20 万字符的异常长文本。当前 embedded 返回限制为 65,536 UTF-8 字节；楼层分页即使每页一条也无法处理这种正文，会整体变成 RESULT_TOO_LARGE。[限制实现](../src/yamibo_mcp/services/embedded_chat/mcp.py#L40)。

长讨论可以按响应大小分段并保留来源位置。这是接口兼容建议，不证明实际用户已遇到该错误，也不扩大到小说产品设计。

## 6. 修正后的页面与 RAG 分工

| 部分 | 修正后应承担的职责 |
|---|---|
| 知识库首页 | 搜索讨论、按板块和日期筛选、查看候选与原文、加入人工资料集；同时显示“我的整理” |
| 资料集 | 保存一组相关讨论及简短备注，例如“灵异百合推荐”“某作品不同评价”；不必先让模型写报告 |
| 助手 | 从自然语言找候选，解释筛选范围，读上下文，归纳推荐/分歧/回答；用户也可以直接选帖交给它 |
| 我的整理 | 可选保存回答、作品清单或笔记，附资料范围、引用和生成时间；继续讨论 |
| 索引维护 | 显示文本准备、向量覆盖和年代分布，按范围补齐；不作为普通使用入口 |

两种进入方式都应成立：

1. 用户知道帖子：选帖 → 助手读完整短讨论/相关窗口 → 回答。
2. 用户不知道帖子：自然语言需求 → 跨归档发现候选 → 显示候选与范围 → 阅读 → 回答。

第二种满足“知道问题但不知道帖子”的需求，这一需求不依赖本地副本是否完整。

检索建议三层：

- **标题、板块、时间及已知名称检索：**立刻利用现有结构化归档；范围明确时直接查。
- **正文关键词检索：**作为首版正式能力，优先复用并验证现有实现，再决定是否改进。本地负载可用于开发验证，不能作为生产性能结论。不在每次请求中偷偷全库预处理。
- **向量检索：**用于口味描述、近义表达、作品名不明确的主题发现，是否补建取决于实际环境和真实问题评测。需与关键词结果结合，读回复上下文后再回答；无需先全量重建。

默认检索单位应尽量呈现“帖子+命中回复+必要上下文”，相邻短回复可以组窗，引用区分被引用内容与当前作者的回复。不要把每个“+1”都变成独立知识。具体分块参数仍需少量真实问题评测，本文不预设万能长度。

主题查找与讨论整理直接对应抽读到的场景，因此建议优先实现。全论坛趋势、意见比例属于另一个统计分析需求，需要明确统计口径和代表性。本地年代分布与同步时间不能用于判断实际项目是否具备这项能力。

## 7. 对原方案的保留、调整与次序

| 原建议 | 本次判断 |
|---|---|
| 明确范围、真实执行反馈、来源及未读说明 | 保留 |
| 普通小范围直接读取，不要求先全量向量化 | 保留；引用身份与长文本分段作为实现细节 |
| 知识库默认展示笔记 | 调整为讨论发现、资料集为主，笔记可选 |
| 正文检索放在后续增强 | 提前到首版核心链路 |
| 复用现有检索索引 | 验证实际环境能力，不依据本地覆盖判断需要重建 |
| 对话只能从手工选好的帖子开始 | 增加自然语言找候选再分析 |
| 先做通用研究报告及后续自动化 | 后置，由真实使用验证需求 |

建议顺序：讨论发现与检索 → 助手读上下文并回答 → 人工资料集与可选成果保存 → 按真实使用评估语义检索增强。提交反馈和任务进度可以同步改进；本地数据缺口与 context 异常不作为前置条件。

这次没有运行 RAG 重建、付费模型、迁移或任何数据库写入，也未修复 context。讨论内容和交流结构支持以上调整，本地缺失不构成调整理由。最终哪些整理结果最常被使用，仍需用上述讨论样例做实际体验验证。
