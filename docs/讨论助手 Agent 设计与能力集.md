# 讨论助手 Agent：职责与运行规则

日期：2026-09-24。本文是[现行总纲](对话—知识库改造方案.md)的 Agent 行为专项；运行框架、RK3588 部署和 Hermes 迁移见[选型决策](对话—知识库%20Agent%20选型与部署决策.md)，首版边界与交付顺序以总纲为准。[旧版](历史草案/讨论助手%20Agent%20设计与能力集-2026-09-23.md)仅作历史记录。范围仅讨论类帖子，本地离线样本不代表线上资料覆盖。

## 一个助手，多动作委托

用户看到一个 Yamibo 助手。它能组合查找、阅读、回答、创建日报规则、归档与导出；不把三条业务拆成拥有不同会话和记忆的多个 Agent。例如“解释这期日报第二条的争议，把其中两篇归档并导出”可以是一项委托，内部形成有依赖的步骤。聊天只负责发起、追问和呈现，长期运行依赖持久化任务。

模型理解自然语言、选择候选和概括意见；程序决定允许的来源、读取和统计边界、预算、授权、任务状态、引用是否合法。模型说“完成了”不构成完成事实。回答、日报、原帖包和个人笔记是不同成果。

## 能力清单

| 业务能力 | 输入与输出 | 必须由程序检查 |
|---|---|---|
| 查找讨论 | 问题、板块／时间、候选上限 → 标题、TID、命中原因 | 仅允许约定的讨论范围；检索方式、失败与未知覆盖可见 |
| 读取讨论 | TID/PID、上下文窗口、预算 → 实际原文与读取回执 | 指定资料模式不得越界；截断和未读位置保留 |
| 读取统计 | 日报目标日、板块 → 活跃指标与统计回执 | 当日窗口、计数口径、已检查资料范围 |
| 生成某日简报 | 日报期次／手动请求 → 有来源的栏目与报告版本 | 内容引用原文回执；数字引用统计回执；保存真实结果 |
| 管理每日规则 | 创建、查看、修改、暂停、恢复 → 规则与下次执行信息 | 配置版本、时区、补跑范围、调度状态 |
| 提出归档／导出计划 | 确定的 TID 集、允许的准备步骤、成果格式 → 完整计划 | 来源与对象冻结，授权覆盖完整计划 |
| 查询任务与成果 | 计划或 Job ID → 各阶段事实、文件、部分失败 | 不把 Job 创建当完成；结果未知时先核查，不盲目重试 |

这是业务能力契约，不要求一行表对应一个模型工具。底层可以复用现有服务；不开放通用 Shell、任意 SQL 或任意网页抓取。有限的论坛列表预览可用于发现待归档候选，须限制板块、页数与来源。

语义检索按实际效果使用。指定 TID 直接读，明确名称优先结构化／关键词检索，模糊意图可尝试语义召回。首版需要好用的正文发现能力，但不把全量向量化作为前提。

## 从 Hermes SOUL.md 沿用的行为约束

旧 Hermes 准则中的“最小、可解释、可恢复的工具序列”继续作为内置助手的工作原则：先判断请求是只读还是操作，区分本地归档、远端现状与派生检索；依据结构化错误、Job 状态和 Recovery 决定后续动作；保存原 Job ID，避免未确认结果时重复创建任务；回答时交代来源、副作用和部分结果的缺口。检索命中须回读原文，不能直接当成证据。

旧文档列出的公开 MCP 工具、`yamibo://guide/*` Resource 和 Hermes 自行编排方式不是内置助手的能力清单。内置助手只能使用当前 Run 暴露的受限工具，范围和授权由宿主、应用服务与工具校验；日报、归档与导出的后台执行由持久化任务承接。公开 MCP 仍可供外部客户端使用，但不能因旧 SOUL.md 列出了某个工具，就认为 Chat 已支持对应自然语言任务。具体可用性以运行时工具注册和端到端验收为准。

2026-09-26 根据旧 SOUL.md 对内置运行提示补齐了实际可执行的纪律：工具成功、计划创建与 Job 完成分别判断；Job 跟踪原始 ID 并按 Recovery 决定等待、读取部分结果、排障或停止；工具失败与明确无结果分别报告；检索片段须回读原文并校验引用；长帖有界读取，遇到重复检索无增益则交付缺口而非继续空转。论坛远端浏览、RAG 建索引、任意公开 MCP Resource 等旧能力没有因此加入内置 Chat；提示词不能替代工具白名单、范围校验、计划审批或真实模型验收。

## 问答运行和停止规则

Run 开始时冻结两种模式之一：发现模式在约定讨论范围内找候选；指定资料模式只允许已选 TID/PID。搜索命中只是候选，只有成功读取后才可作为叙述证据。相同请求标识如果输入、范围或关联报告版本变化，返回冲突。历史回答和日报摘要是派生材料，关键论据仍须追溯到原回复。

1. 解析问题，建立初始范围和阅读预算；缺写入目标时可先找候选，写入前必须确定对象。
2. 搜索候选并逐步读首帖、命中回复、相关前后楼层和更正；长帖按问题窗口分段。
3. 对每个主张判断是否已有足够原文支持；有明确关键缺口时做针对性补读。
4. 生成回答并由程序校验引用 ID、来源范围和实际读取事实；观点是否受来源支持另用真实样例验收。

| 条件 | 结束或继续方式 |
|---|---|
| 关键问题有足够材料支持 | 回答，注明实际已读范围、来源及不确定性 |
| 候选相关，但首帖或关键更正未读 | 在预算内补读，再判断；不直接概括候选片段 |
| 预算已到，或重复检索不增加有效材料 | 输出部分答案与缺口，结束本次 Run |
| 检索／读取工具失败或无权限 | 报告能力故障及可恢复动作，不能称“无相关讨论” |
| 明确检索成功且范围内无结果 | 报告该范围及方法下未找到，不外推到全论坛 |
| 写入目标、操作或导出范围仍有歧义 | 暂停该写入步骤，请用户选择；独立的只读部分可先交付 |
| Job 长时间运行 | 保存回执并交给任务卡；不占住模型等待名额 |

程序应在工具端限制同一失败调用的重试次数、单次查询范围和读取量；模型决定“还缺什么”，工具返回可解释的边界与下一步。Run 不再因累计模型请求数或工具调用数达到任意额度而停止；超时或人为停止后，已创建 Job 的状态独立显示。

## 多动作委托的衔接

把用户请求拆成有序业务步骤，并明确每步的输入、条件和终态。纯阅读可先完成；依赖归档完成的导出交给持久化固定任务链。计划冻结目标和来源，授权时展示所有将产生的操作。用户说“这期日报前三篇”时，绑定报告 ID、版本、栏目、顺序和最终 TID；栏目不明才请求选择。不能把日报正文中出现的所有帖子自动升级为写入目标。

可在同一委托中“解释报告→归档两篇→导出成功对象”。解释可以先返回；后两个阶段由后台继续，失败逐帖汇总。普通开放式“归档后再研究”若没有持久化续作能力，应清楚说明届时需新请求；固定的“归档后导出”在首版必须自动衔接。

## 日报 Agent 的角色

定时规则由程序保存和触发。Agent 不在会话里睡眠至次日，而是在某日期的日报 Job 内对程序选出的候选做有限阅读和编辑摘要。活跃排序来自可复核指标，模型只能生成单列的“值得看”推荐及理由。日报保存统计回执和原文引用；追问时绑定指定报告版本。日报规则与数据就绪契约见[专项](讨论助手—日报与归档导出能力修正.md)。

## 验收场景

- [《少女的港湾》样本](../data/threads/573256/metadata.json)有后续更正；助手必须补读相关回复，不能只凭首帖及合法引用下结论。
- 发现模式能从问题找相关讨论；指定三篇模式不得带入第四篇。无向量时仍可发现和阅读。
- 长归档任务在后台运行时，另一个短查询仍能完成；关闭页面后回来能读到原 Job 状态。
- “解释日报争议，并归档／导出所选两篇”形成组合委托，解释与操作结果分别有明确状态。
- 停用检索、无结果、预算用尽和不明确写入对象分别产生不同的结束状态。

本文件定义目标行为；当前内置助手已实现其中一部分能力，未覆盖的场景仍须按运行时工具和端到端测试区分。
