# 部署指南 & 运维手册

> 版本：1.2.0 | 更新日期：2026-09-12

## 1. 环境要求

| 依赖 | 版本要求 | 说明 |
|------|---------|------|
| Python | >= 3.11 | 推荐 3.13 |
| uv | 最新版 | Python 包管理器 |
| PostgreSQL | 15+ | 推荐配合 `pgvector` |
| 操作系统 | macOS / Linux | Windows 未测试 |
| 网络 | 可访问 bbs.yamibo.com | 远程归档需要 |

RAG 相关补充：

- 当前主路径为 PostgreSQL + `pgvector`
- 若要生成 embedding，需要配置支持 `/v1/embeddings` 的 RAG API；未单独配置时会回退到 `YAMIBO_LLM_BASE_URL` / `YAMIBO_LLM_API_KEY`

数据库说明：

- 本地空配置默认 SQLite，适合快速启动和轻量单机归档
- Docker 与生产环境推荐 PostgreSQL；设置 `YAMIBO_DB_BACKEND=postgres` 时必须同时设置 `YAMIBO_DB_URL=...`

### 当前数据库变更门禁

仅提交 GitHub 不会直接修改数据库。若远端会拉取、构建并启动当前工作区代码，则可能发生数据库变更：当前工作区包含 Alembic revision `016_add_jobs_started_at`，它会为 PostgreSQL 的 `jobs` 表增加可空的 `started_at` 列，并更新 `alembic_version`。

当前启动路径会在应用启动阶段调用 schema bootstrap；`yamibo-daemon` 的 Web 应用启动、显式执行 `yamibo-init-db`，以及部分使用默认数据库连接的 CLI/MCP 调用，都可能触发尚未应用的迁移。迁移只执行一次且不会重新抓取论坛内容，但仍属于生产数据库 DDL 变更。

因此，在“暂不修改生产数据库”的阶段：

- 不要把包含 `016_add_jobs_started_at` 的工作区直接交给 NAS 自动部署。
- 不要在生产环境执行 `docker compose run --rm yamibo yamibo-init-db`。
- 保持当前已部署镜像和数据库版本；若只提交文档，确保部署流水线不会因该提交重建并启动包含迁移的代码。
- 等明确批准数据库变更后，再先备份、在隔离库验证迁移，再安排生产发布。

`git push`、`docker compose build` 本身不改数据库；真正的风险点是连接生产数据库的进程启动或显式迁移命令。

## 2. 安装

### 2.1 克隆与安装依赖

```bash
git clone <repo-url> yamibo
cd yamibo

# 安装所有依赖（含开发依赖）
uv sync --extra dev
```

### 2.2 配置

#### 方式一：配置文件

复制 `yamibo.local.example.json` 为 `yamibo.local.json`（不提交后者到版本控制）：

```json
{
  "yamibo": {
    "cookie_file": ".cookie"
  },
  "llm": {
    "base_url": "https://api.openai.com/v1",
    "api_key": "sk-your-key",
    "model": "gpt-4.1-mini"
  }
}
```

如需多账号池，可在 `yamibo.account_pool` 里补充多个账号。每个账号建议使用独立的 `cookie_file`，并用 `permission_level` 标记阅读权限；推荐按 `0/10/20/...` 这种梯队配置，`0` 是最低权限。系统会优先用低权限账号做普通抓取，只有在权限不足或列表/搜索场景下才切换到更高权限账号。

#### Mihomo 代理池（可选）

如需为每个 thread 归档任务绑定独立代理 IP，需自行运行 mihomo 代理（如 Clash Verge），然后在 `yamibo.proxy_pool` 中配置：

```json
{
  "yamibo": {
    "proxy_pool": {
      "enabled": true,
      "controller_url": "http://127.0.0.1:9090",
      "secret": "",
      "proxy_url": "http://127.0.0.1:7890",
      "selector_group": "yamibo",
      "test_url": "https://www.gstatic.com/generate_204",
      "test_timeout_ms": 3000,
      "failure_policy": "fail_open",
      "allowed_patterns": [],
      "denied_patterns": [],
      "max_delay_ms": 0
    }
  }
}
```

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `enabled` | `false` | 开关，默认关闭不影响现有行为 |
| `controller_url` | `""` | mihomo controller REST API 地址 |
| `secret` | `""` | controller auth secret（空则不加 Authorization header） |
| `proxy_url` | `""` | 代理地址，传给 HTTP 请求和图片下载 |
| `selector_group` | `""` | mihomo 中类型为 Selector 的代理组名 |
| `test_url` | `gstatic.com/generate_204` | 节点延迟测试 URL |
| `test_timeout_ms` | `3000` | 延迟测试超时（毫秒） |
| `failure_policy` | `"fail_open"` | mihomo 故障时直连；HTTP 444 反爬始终 fail-closed |
| `allowed_patterns` | `[]` | 正则白名单，非空时节点必须匹配至少一项 |
| `denied_patterns` | `[]` | 正则黑名单，匹配任意一项即排除 |
| `max_delay_ms` | `0` | 延迟上限（毫秒），超过的排除（0 = 不限制） |

验证配置：`uv run yamibo-archiver check-proxy-pool`

#### Cookie 定时刷新

`yamibo.cookie_refresh_interval_hours`（默认 `12`）控制 cookie 文件的定时刷新周期。设为 `0` 关闭。刷新时机：`borrow_yamibo_client()` 创建客户端前检查，到期则删除 cookie 文件，`YamiboClient` 构造时会自动重新登录。

```json
{
  "yamibo": {
    "cookie_refresh_interval_hours": 12
  }
}
```

#### 方式二：环境变量

```bash
export YAMIBO_LLM_API_KEY="sk-your-key"
export YAMIBO_LLM_MODEL="gpt-4.1-mini"
```

或复制 `.env.example` 为 `.env` 并编辑。

如需启用或调整 RAG，可追加：

```bash
export YAMIBO_RAG_ENABLED=true
export YAMIBO_RAG_BASE_URL="https://api.openai.com/v1"
export YAMIBO_RAG_API_KEY="sk-your-rag-key"
export YAMIBO_RAG_EMBEDDING_MODEL="text-embedding-3-small"
export YAMIBO_RAG_EMBEDDING_DIMENSIONS=512
```

说明：

- `YAMIBO_LLM_*` 仅用于标题解析等内部 LLM 调用，不是 Web Chat 的 Hermes 配置
- `YAMIBO_RAG_*` 独立用于 `/v1/embeddings` embedding
- 如果不设置 `YAMIBO_RAG_BASE_URL` / `YAMIBO_RAG_API_KEY`，RAG 会自动回退到 `YAMIBO_LLM_BASE_URL` / `YAMIBO_LLM_API_KEY`

#### Web Chat / Hermes Runs

Web Chat 使用 Hermes 的 Runs 协议，不使用旧的 `chat/completions` 或 SSE MCP 配置。配置以下环境变量：

```bash
export YAMIBO_HERMES_HOST="127.0.0.1"
export YAMIBO_HERMES_PORT=8642
export YAMIBO_HERMES_API_KEY="your-hermes-key"
export YAMIBO_HERMES_MODEL="hermes-agent"
```

Yamibo 会通过 Hermes `/health`、`/v1/capabilities`、`/v1/models` 完成能力检查；对话使用 `/api/sessions`、`/v1/runs`，并通过 `/v1/runs/{run_id}/events`、`/v1/runs/{run_id}/stop`、`/v1/runs/{run_id}/approval` 完成流式运行控制。API Key 只由服务端读取并转发，浏览器请求和响应不应携带或显示该 key。

### 2.3 论坛 Cookie

在浏览器中登录 bbs.yamibo.com，复制 Cookie 到 `.cookie` 文件：

```
cookie
```

或使用单行格式：`name1=value1; name2=value2`

```bash
uv run yamibo-init-db
```

## 3. Docker 部署（推荐）

Docker 部署会启动 PostgreSQL/pgvector 与 Yamibo Daemon。Daemon 同时负责后台任务消费和 Web 控制台。项目运行数据建议通过宿主机 `data/` 目录外挂，PostgreSQL 数据默认使用 Docker named volume，也可以切换为宿主机目录。

### 3.0 安全边界

1.0 默认将 PostgreSQL、Web 和 MCP 端口绑定到 `127.0.0.1`。Web 控制台包含配置修改、任务创建和数据删除能力，MCP 也可以创建有副作用的后台任务；两者都不能在没有额外访问控制时直接暴露到互联网。

远程部署应使用以下拓扑：

```text
Internet -> TLS reverse proxy / VPN / identity-aware proxy -> Yamibo loopback ports
                                                    \-> PostgreSQL remains private
```

只有在外部安全层已经就绪时，才可在 `.env` 中显式修改绑定地址：

```env
YAMIBO_WEB_BIND_HOST=0.0.0.0
YAMIBO_MCP_BIND_HOST=0.0.0.0
```

不要把 `POSTGRES_BIND_HOST` 改为 `0.0.0.0`。跨主机数据库连接应使用私有网络、TLS 和独立的高强度凭据。

Yamibo 当前不暴露 Agent Run 查询、审批或取消接口。NAS 部署优先保持 Yamibo 监听
`127.0.0.1`，由已经启用 TLS 和登录认证的反向代理转发；不要绕过代理开放 8765 端口。

### 3.1 准备目录和配置

```bash
cp .env.docker.example .env
cp yamibo.local.example.json data/yamibo.local.json
mkdir -p data data/exports data/novel_exports data/cookies data/backups
```

Cookie 文件放在 `data/cookies/` 下。容器内路径对应 `/app/data/cookies/`。如果使用多账号池，建议为每个账号显式配置独立 cookie 文件，例如 `/app/data/cookies/primary.cookie`、`/app/data/cookies/secondary.cookie`。

创建或调整 `yamibo.local.json`：

```json
{
  "yamibo": {
    "cookie_file": "/app/data/cookies/primary.cookie",
    "novel_author_only_max_pages": 50,
    "novel_author_only_page_delay_seconds": 0.5,
    "image_backfill_enabled": false,
    "image_backfill_dry_run": true,
    "image_backfill_forum_id": 5,
    "image_backfill_auto_interval_seconds": 60,
    "image_backfill_daily_limit": 100,
    "image_backfill_max_pages": 1
  },
  "export": {
    "dir": "/app/data/exports",
    "novel_txt_dir": "/app/data/novel_exports",
    "novel_txt_include_filtered_notes": false,
    "novel_txt_debug_markers": false
  }
}
```

数据库、端口、LLM/Hermes 和 RAG 建议放在 `.env`，不要写入 `yamibo.local.json`。

`image_backfill_enabled` 在 1.2.0 首次部署时应保持 `false`。先在隔离 PostgreSQL 或备份库验证两个独立连接的 advisory lock 互斥、单次候选扫描 `<3s`；生产 canary 使用 dry-run、daily limit 1，并确认候选查询并发数不超过 1、帖子列表 p95 `<1s` 后再逐步开启。

### 3.2 data 目录外挂

默认 compose 配置：

```env
YAMIBO_DATA_BIND=./data
```

容器内路径固定为 `/app/data`。常见持久化内容：

| 容器路径 | 宿主机路径 | 说明 |
|----------|------------|------|
| `/app/data/exports` | `./data/exports` | 通用导出 |
| `/app/data/novel_exports` | `./data/novel_exports` | 轻小说 TXT 导出 |

Compose 默认只挂载 `YAMIBO_DATA_BIND` 到 `/app/data`，不假设宿主机存在特定的 macOS 或 Linux 目录。如需将导出同步到其他磁盘，应在本地 `docker-compose.override.yml` 中增加显式挂载，不要将机器专用路径写入主 Compose 文件。
| `/app/data/cookies` | `./data/cookies` | 多账号 cookie |
| `/app/data/backups` | `./data/backups` | 备份输出 |
| `/app/data/staging` | `./data/staging` | 临时归档工作区 |
| `/app/data/title_hints.json` | `./data/title_hints.json` | 标题提示 |

PostgreSQL 默认使用 named volume：

```env
YAMIBO_POSTGRES_DATA=yamibo_postgres_data
```

如果希望数据库文件也外挂到宿主机目录，改为：

```env
YAMIBO_POSTGRES_DATA=./postgres-data
```

首次切换前请停止容器，并确认目标目录为空或已完成数据迁移。

### 3.3 首次启动

```bash
docker compose build
docker compose up -d postgres
docker compose run --rm yamibo yamibo-init-db
docker compose up -d yamibo
```

访问 Web 控制台：

```text
http://localhost:8765
```

该地址默认只能从 Docker 宿主机访问。需要远程访问时，按 3.0 节配置反向代理或 VPN，不要直接开放容器端口。

健康检查：

```bash
curl http://localhost:8765/api/health
```

### 3.4 外接 Hermes Docker（对话页优先场景）

Web Chat 使用 Hermes Runs 协议。Hermes 需要提供 `/health`、`/v1/capabilities`、`/v1/models`，以及 `/api/sessions`、`/v1/runs` 和 `/v1/runs/{run_id}/events|stop|approval` 接口；Web Chat 不依赖 `/v1/chat/completions`。

容器内的 Yamibo 通过服务名访问同一 compose 网络中的 Hermes：

```env
YAMIBO_HERMES_HOST=hermes
YAMIBO_HERMES_PORT=8000
YAMIBO_HERMES_API_KEY=your-hermes-key
YAMIBO_HERMES_MODEL=hermes
```

如果 Hermes 在同一个 compose 中，添加类似服务：

```yaml
services:
  hermes:
    image: your-hermes-image
    container_name: hermes
    ports:
      - "8000:8000"
    restart: unless-stopped
```

如果 Hermes 已在另一个 Docker compose 中，建议使用共享网络：

```bash
docker network create llm-net
docker network connect llm-net hermes
```

然后在 `docker-compose.yml` 为 `yamibo` 增加该外部网络，或启动后执行：

```bash
docker network connect llm-net yamibo-app
```

如果 Hermes 运行在宿主机：

```env
YAMIBO_HERMES_HOST=host.docker.internal
YAMIBO_HERMES_PORT=8000
```

compose 已包含 `host.docker.internal:host-gateway`，Linux Docker Engine 下也可使用该地址。

如果 Yamibo 在宿主机、Hermes 也在宿主机，通常使用 `YAMIBO_HERMES_HOST=127.0.0.1`；如果 Yamibo 在容器、Hermes 在另一 Docker 网络，使用 Hermes 的容器名或网络别名，并将两个容器接入同一网络。`YAMIBO_HERMES_API_KEY` 只放在服务端环境，浏览器不保存、不提交。

### 3.5 RAG embedding 与 Hermes 的关系

Hermes Runs 与 RAG embedding 是两条独立链路。若 Hermes 不提供 `/v1/embeddings`，不要把 `YAMIBO_HERMES_*` 当作 RAG 配置；可以先关闭 RAG：

```env
YAMIBO_RAG_ENABLED=false
```

如果需要 RAG，请把 embedding 单独接到支持 `/v1/embeddings` 的服务，并配置 `YAMIBO_RAG_*`：

```env
YAMIBO_RAG_ENABLED=true
YAMIBO_RAG_BASE_URL=https://api.openai.com/v1
YAMIBO_RAG_API_KEY=sk-your-embedding-key
YAMIBO_RAG_EMBEDDING_MODEL=text-embedding-3-small
YAMIBO_RAG_EMBEDDING_DIMENSIONS=512
```

### 3.6 日常运维

查看日志：

```bash
docker compose logs -f yamibo
```

重启：

```bash
docker compose restart yamibo
```

#### 3.6.1 从 GitHub 拉取后（当前不改数据库）

先在 NAS 上确认工作区没有未预期的本地改动，再只做快进拉取：

```bash
cd /path/to/Yamibo
git status --short
old_commit=$(git rev-parse HEAD)
git pull --ff-only
git diff --name-status "$old_commit"..HEAD
docker compose config --quiet
docker compose ps
git status --short
```

`git pull` 只更新工作区文件，不会直接连接数据库。当前 Compose 不把源代码目录挂载进容器，所以拉取完成后，正在运行的容器仍使用原镜像。

如果本次提交只改文档，可以保持容器不动，并做只读检查：

```bash
curl -fsS http://127.0.0.1:8765/api/health
curl -fsS http://127.0.0.1:8765/api/daemon/status
```

本阶段不要执行 `docker compose build`、`docker compose up -d`、`docker compose restart` 或
`docker compose run --rm yamibo yamibo-init-db`。如果提交包含 Python、前端、Dockerfile 或
`alembic/` 改动，拉取后应停在这里；这表示“代码已拉取、生产仍运行旧镜像”，不表示新代码已经部署。

在“不修改数据库”的目标下，本次操作满足以下条件才算完成：目标提交已拉取、没有未预期的工作区改动、现有容器持续 healthy、健康和 Daemon 接口返回成功，并且 PostgreSQL 的
`alembic_version` 与操作前一致。最后一项应通过操作前后只读查询比较，不能仅凭 GitHub 提交或镜像标签判断。

#### 3.6.2 已批准数据库变更后的发布流程

只有明确允许改库时，才按下面顺序发布。当前 `016_add_jobs_started_at` 只是为
`jobs` 增加可空列，通常不需要重建大表，但仍会获取数据库锁，必须安排维护窗口。

1. **发布前记录状态并确认备份**。在 NAS 项目目录执行：

   ```bash
   cd /path/to/Yamibo
   git status --short
   docker compose config --quiet
   docker compose ps
   docker compose exec -T postgres \
     psql -U yamibo -d yamibo -Atc \
     "SELECT version_num FROM alembic_version;" \
     | tee /tmp/yamibo-alembic-before.txt
   ```

   按 [PostgreSQL 备份](#postgresql-备份) 生成 custom-format dump，保存到独立磁盘，
   并完成 `sha256sum` 和 `pg_restore --list` 校验。备份文件和校验结果必须能在维护窗口
   内找到；不要把“已经执行过备份”当作验证证据。

2. **停止会访问数据库的应用容器**，保留 PostgreSQL 运行：

   ```bash
   docker compose stop yamibo yamibo-mcp
   ```

   这会暂时停止 Web、Daemon 和 MCP。确认反向代理已进入维护状态，避免迁移期间产生新
   请求或 Job。

3. **快进拉取并构建新镜像**：

   ```bash
   git pull --ff-only
   docker compose build
   ```

   如果 `git pull` 有冲突、工作区出现未预期改动或构建失败，应停止发布并保留旧容器，
   不要继续执行迁移。

4. **使用新镜像单独执行迁移**：

   ```bash
   docker compose run --rm --no-deps yamibo yamibo-init-db
   ```

   命令成功退出后立即核对版本：

   ```bash
   docker compose exec -T postgres \
     psql -U yamibo -d yamibo -Atc \
     "SELECT version_num FROM alembic_version;" \
     | tee /tmp/yamibo-alembic-after.txt
   docker compose exec -T postgres \
     psql -U yamibo -d yamibo -Atc \
     "SELECT column_name, is_nullable FROM information_schema.columns WHERE table_schema='public' AND table_name='jobs' AND column_name='started_at';"
   ```

   预期版本包含 `016_add_jobs_started_at`。如果迁移报错、版本没有变化或出现锁超时，
   不要启动新应用；保留日志，必要时依据备份执行隔离恢复和回滚评估。

5. **启动新容器并等待健康检查**：

   ```bash
   docker compose up -d yamibo yamibo-mcp
   docker compose ps
   curl -fsS http://127.0.0.1:8765/api/health
   curl -fsS http://127.0.0.1:8765/api/daemon/status
   ```

   应用启动也会再次检查 schema，但已应用的迁移不会重复执行。先看启动日志，确认没有
   migration、连接池或反复重启错误：

   ```bash
   docker compose logs --tail=200 yamibo yamibo-mcp
   ```

   `yamibo-mcp` 的健康检查只验证 `/sse` 是否及时返回 HTTP 响应头，不等待 SSE 长连接
   结束。若日志中 `/sse` 返回 `200 OK` 但容器仍为 `unhealthy`，先查看
   `docker inspect` 的健康检查输出，确认是否为网络连接失败，而不是流式响应超时。

6. **完成验收**。下面条件全部满足，才算本次发布完成：

   - `git rev-parse HEAD` 是目标提交，`git status --short` 没有未预期改动；
   - `alembic_version` 已到目标 revision，且 `jobs.started_at` 列存在；
   - `yamibo`、`yamibo-mcp`、`postgres` 持续 healthy，没有迁移或连接错误；
   - `/api/health` 返回 `ok=true`、数据库为预期 PostgreSQL，`/api/daemon/status` 返回
     `daemon_alive=true`；
   - Web 能打开论坛列表、帖子详情和一个已有归档，至少完成一次只读 API 抽查；
   - 若恢复 Job 处理，观察一个 Job 从读取到完成或明确失败，确认队列数量和错误率没有
     异常增长；
   - 维护窗口结束后，反向代理访问、MCP 连接（如使用）和备份目录均正常。

   迁移是否完成以数据库中的 `alembic_version` 和实际列结构为准，不以 GitHub 提交、
   镜像标签或容器“启动成功”单独判断。完成验收后再删除旧镜像；备份至少保留到下一次
   备份成功且回滚窗口关闭。

当前工作区的 `yamibo` 启动会做一次 schema bootstrap，因此不能通过跳过
`yamibo-init-db` 来保证数据库不变；不允许改库时，应继续运行现有镜像，不要启动包含
`016_add_jobs_started_at` 的新镜像。

如果目标数据库曾运行过已移除的 Phase B/C Runtime，当前版本会通过 009-012
兼容 revision 解析旧迁移记录，并由 013 迁移清理旧 Runtime 表。执行升级前仍应
先完成 PostgreSQL 备份；迁移只处理旧 Agent Runtime 表，不影响论坛、归档、Job
和 RAG 业务表。

手动进入容器运行 CLI：

```bash
docker compose run --rm yamibo yamibo-archiver browse-forum-page --page 1
```

### 3.7 数据库备份、恢复与迁移

#### PostgreSQL 备份

推荐用 `pg_dump` 从 postgres 容器导出：

```bash
docker compose exec postgres pg_dump -U yamibo -d yamibo -Fc -f /tmp/yamibo.dump
docker compose cp postgres:/tmp/yamibo.dump ./data/backups/yamibo.dump
```

也可以导出 SQL 文本：

```bash
docker compose exec postgres pg_dump -U yamibo -d yamibo -f /tmp/yamibo.sql
docker compose cp postgres:/tmp/yamibo.sql ./data/backups/yamibo.sql
```

PostgreSQL 备份只包含结构化记录、索引和 Job 状态，不包含 `data/threads/`、`data/shared/`、导出包等文件。备份文件应放在与 PostgreSQL 数据目录不同的磁盘或共享目录，并保留 SHA-256 校验值。

#### PostgreSQL 隔离恢复演练（推荐）

首次演练不要覆盖生产库。当前归档文件规模较大时，先做数据库演练即可，不需要复制全部图片。以下示例在同一个 PostgreSQL 服务中创建临时数据库；如果空间不足，应改用另一块磁盘或另一台 PostgreSQL，不要压缩生产数据目录。

先记录关键表数量，再生成 custom dump：

```bash
PGUSER=yamibo
PGDB=yamibo
DRILL_BACKUP_DIR=/path/to/separate-backup-disk/yamibo-drill
BACKUP="$DRILL_BACKUP_DIR/forum_$(date +%Y%m%d_%H%M%S).pgdump"

mkdir -p "$DRILL_BACKUP_DIR"
for table in forums threads floors content_blocks assets jobs job_events system_state; do
  docker compose exec -T postgres \
    psql -U "$PGUSER" -d "$PGDB" -Atc \
    "SELECT '$table', count(*) FROM $table;"
done > "$DRILL_BACKUP_DIR/source.counts"

docker compose exec -T postgres \
  pg_dump -U "$PGUSER" -d "$PGDB" -Fc -Z 3 > "$BACKUP"
sha256sum "$BACKUP" | tee "$BACKUP.sha256"
docker compose exec -T postgres \
  pg_restore --list < "$BACKUP" > "$BACKUP.list"
```

创建临时数据库并恢复。`DRILL_DB` 只能是临时库名，连接 URL 中的凭据替换为实际配置：

```bash
DRILL_DB="yamibo_restore_drill_$(date +%Y%m%d_%H%M%S)"

docker compose exec -T postgres \
  createdb -U "$PGUSER" -O "$PGUSER" "$DRILL_DB"
docker compose exec -T postgres \
  pg_restore -U "$PGUSER" -d "$DRILL_DB" \
  --exit-on-error --no-owner --no-acl < "$BACKUP"

docker compose run --rm --no-deps \
  -e YAMIBO_DB_BACKEND=postgres \
  -e YAMIBO_DB_URL="postgresql://yamibo:yamibo@postgres:5432/$DRILL_DB" \
  yamibo yamibo-init-db
```

验证恢复结果，不要在演练库启动 Daemon：

```bash
for table in forums threads floors content_blocks assets jobs job_events system_state; do
  docker compose exec -T postgres \
    psql -U "$PGUSER" -d "$DRILL_DB" -Atc \
    "SELECT '$table', count(*) FROM $table;"
done > "$DRILL_BACKUP_DIR/drill.counts"
diff -u "$DRILL_BACKUP_DIR/source.counts" "$DRILL_BACKUP_DIR/drill.counts"

docker compose exec -T postgres \
  psql -U "$PGUSER" -d "$DRILL_DB" -Atc \
  "SELECT version_num FROM alembic_version;"

docker compose run --rm --no-deps \
  -e YAMIBO_DB_BACKEND=postgres \
  -e YAMIBO_DB_URL="postgresql://yamibo:yamibo@postgres:5432/$DRILL_DB" \
  yamibo yamibo-archiver read-system-status
```

演练环境预期 `database.ok=true`，但 `daemon_alive=false`。确认无误后只删除临时数据库：

```bash
docker compose exec -T postgres \
  dropdb -U "$PGUSER" --if-exists "$DRILL_DB"
```

如果希望验证 Web 读取，再将 Web 临时绑定到 loopback 端口，使用同一个 `DRILL_DB` 和只读数据目录；不要启动 `yamibo-daemon`，不要让恢复库执行远端任务。

#### 归档文件快照与抽样验证

`data/` 与 PostgreSQL 是两套恢复对象。`/api/forums` 返回的 `archive_size_bytes` 是已保存的聚合值，不是每次请求都重新扫描磁盘。大规模归档优先使用 NAS 的 Btrfs、ZFS 或存储系统只读快照；没有快照时，再复制到独立恢复目录：

```bash
rsync -aHAX --numeric-ids --info=progress2 \
  --exclude='cookies/***' \
  --exclude='backups/***' \
  --exclude='staging/***' \
  /path/to/data/ /path/to/restore-data/
```

要验证数据库和文件处于同一时间点，先在 Web 任务页暂停全部 Job，等待 `running=0`，再停止 `yamibo` 容器后创建数据库备份和文件快照。仅做 PostgreSQL 演练时不需要停止服务。

文件恢复不必每次对全部文件计算哈希。建议从动漫区、漫画区和海域区各选几个 `tid`，检查对应的 `metadata.json`、`context.md` 和至少一张本地图片；完整校验可作为低频灾备演练，而不是日常维护步骤。Cookie 不应复制到共享演练目录，应单独加密保存。

#### 生产库恢复

生产库恢复不是首次演练路径。只有在备份校验、隔离恢复和文件抽样均通过，并且已进入维护窗口后，才可以停止 `yamibo`、确认目标数据库和数据目录，再执行恢复与 `yamibo-init-db`。不要把 `dropdb yamibo` 作为默认演练命令；生产切换前必须再次确认数据库名、容器项目和备份文件路径。

#### 从本机 PostgreSQL 迁移到 Docker PostgreSQL

在旧环境导出：

```bash
pg_dump "$YAMIBO_DB_URL" -Fc -f ./data/backups/yamibo-local.dump
```

导入 Docker：

```bash
docker compose up -d postgres
docker compose cp ./data/backups/yamibo-local.dump postgres:/tmp/yamibo-local.dump
docker compose exec postgres createdb -U yamibo yamibo_import_drill
docker compose exec postgres pg_restore -U yamibo -d yamibo_import_drill \
  --exit-on-error --no-owner --no-acl /tmp/yamibo-local.dump
docker compose run --rm --no-deps \
  -e YAMIBO_DB_BACKEND=postgres \
  -e YAMIBO_DB_URL=postgresql://yamibo:yamibo@postgres:5432/yamibo_import_drill \
  yamibo yamibo-init-db
```

先按“隔离恢复演练”验证 `yamibo_import_drill`，确认无误后再安排生产切换。不要在已有生产数据库上直接执行 `dropdb`。

#### 迁移文件归档数据

数据库只保存结构化记录和索引。归档文件、图片、导出、cookie、备份等在 `data/`。迁移机器时需要同时复制：

```bash
rsync -a ./data/ user@new-host:/path/to/Yamibo/data/
rsync -a ./yamibo.local.json user@new-host:/path/to/Yamibo/yamibo.local.json
```

目标机器启动后执行：

```bash
docker compose run --rm yamibo yamibo-init-db
docker compose up -d
```

#### 历史 file-only 归档补回数据库

如果只迁移了 `data/threads/<tid>/metadata.json` / `context.md`，但数据库没有对应记录，按本指南后文“历史 file-only 归档补回数据库”执行 `scripts/enqueue_missing_db_thread_sync.py`，让 daemon 重新同步远端元数据。

## 4. 启动服务

系统由两个独立进程组成：

| 进程 | 生命周期 | 说明 |
|------|---------|------|
| MCP Server | 由 LLM 客户端触发，随会话长期运行 | 处理 MCP 请求，创建任务到 PostgreSQL |
| Daemon | 独立后台进程，支持单次或持续运行 | 轮询 PostgreSQL 消费任务，内嵌 Web 控制台 |

### 3.1 启动 Daemon（后台任务消费 + Web 控制台）

```bash
# 持续运行（默认模式，内嵌 Web 控制台）
uv run yamibo-daemon

# 单次执行后退出（测试用）
uv run yamibo-daemon --once

# 指定 Daemon ID
uv run yamibo-daemon --worker-id my-daemon

# 不启动嵌入式 Web 控制台
uv run yamibo-daemon --no-web
```

Daemon 启动后，Web 控制台自动在 `http://127.0.0.1:8765` 提供服务。

### 3.2 MCP Server（由 LLM 客户端自动启动）

MCP Server 不需要手动启动。配置好 LLM 客户端后，客户端会自动调用：

```bash
uv run yamibo-archiver stdio
```

支持的传输模式：

```bash
uv run yamibo-archiver stdio                        # 默认 stdio
uv run yamibo-archiver stdio --transport sse         # SSE
uv run yamibo-archiver stdio --transport streamable-http  # HTTP
```

### 3.3 CLI 直接调用（无需启动服务）

核心 MCP 工具有对应的命令行入口，返回 JSON 结果；长任务命令只创建 job，仍需 daemon 消费：

```bash
uv run yamibo-archiver browse-forum-page --page 1
uv run yamibo-archiver search-threads --query "关键词"
uv run yamibo-archiver inspect-remote-thread --tid 572313
uv run yamibo-archiver create-thread-archive-job --tid 572313
uv run yamibo-archiver job-status <job_id>
uv run yamibo-archiver wait-for-job <job_id>
uv run yamibo-archiver read-resource "yamibo://threads/572313/summary"
```

### 3.4 历史 file-only 归档补回数据库

如果 `data/threads/<tid>/` 下已有 `metadata.json` / `context.md`，但数据库里没有对应 `threads` 记录，建议优先走远端 `sync_thread` 重同步，而不是手工改库。

```bash
# 先看计划，不写入任务
uv run python scripts/enqueue_missing_db_thread_sync.py --dry-run --batch-size 100 --max-batches 2

# 正式按批次创建 sync_thread jobs，并让 daemon 自动补 forum_id / floors / title_parse / local_reply_count
uv run python scripts/enqueue_missing_db_thread_sync.py --batch-size 100 --max-batches 2
```

说明：

- 不需要手动传 `forum_id`，系统会从远端线程页面面包屑/论坛链接自动提取
- 这些 tid 处理完成前，不要运行 `cleanup-orphan-thread-dirs`

## 6. 运维操作

### 5.1 数据库备份

```bash
# 创建带时间戳的备份
uv run yamibo-backup-db

# 指定目标目录
uv run yamibo-backup-db --dest-dir /path/to/backups

# 同时备份 Cookie 文件
uv run yamibo-backup-db --copy-cookie

# 指定保留数量（默认 20）
uv run yamibo-backup-db --keep-count 10
```

备份文件格式：PostgreSQL 为 `forum_YYYYMMDD_HHMMSS.pgdump`

### 5.2 历史 SQLite -> PostgreSQL 迁移

ETL 命令：

```bash
uv run python scripts/migrate_sqlite_to_postgres.py \
  --source-db data/forum.db \
  --target-db-url "$YAMIBO_DB_URL" \
  --schema public
```

迁移脚本会导入源表、同步自增序列、重建搜索索引，并执行 `ANALYZE`。

### 5.3 清理过期数据

```bash
# 清理过期 staging 目录和临时导出文件
uv run yamibo-maintenance-cleanup

# 查看将要清理的内容（不实际删除）
uv run yamibo-maintenance-cleanup --dry-run

# 自定义过期时间
uv run yamibo-maintenance-cleanup --staging-older-than-hours 24
```

### 5.3 数据重置

```bash
# 查看将要删除的内容
uv run yamibo-reset-data --dry-run

# 确认删除并重建空数据库
uv run yamibo-reset-data --yes

# 删除但不重建数据库
uv run yamibo-reset-data --yes --no-reinit-db
```

### 5.4 通过 Web 控制台创建任务

Web 控制台（默认 `http://127.0.0.1:8765`）提供以下运维操作：

- **创建同步任务**：输入 tid 或 URL
- **创建导出任务**：选择策略
- **批量同步**：输入页码范围
- **标题复核**：修正解析结果
- **系列管理**：合并、确认系列
- **删除归档**：删除帖子或系列
- **RAG 管理**：查看索引覆盖、创建单贴 `rag_index` 任务、调试本地检索

## 8. 已知约束

### 7.1 论坛维护窗口

- **时间**：每天 5:30-6:30（UTC+8）
- **影响**：此时访问论坛返回维护页面
- **系统行为**：抛出 `RemoteMaintenanceError`，任务标记为 failed

### 7.2 搜索限流

- **限制**：约 10 秒/次
- **影响**：频繁搜索会被论坛限流
- **系统行为**：远端失败时自动降级到本地 FTS 搜索

### 7.3 Cookie 过期

- Cookie 有效期取决于论坛设置
- 配置 `login.username` 和 `login_password` 可启用自动登录

## 9. 故障排除

| 症状 | 原因 | 解决 |
|------|------|------|
| 任务反复 retrying 后 failed + REMOTE_SOFT_BLOCK | 远端返回了反爬/语义提示，或旧版本把帖子删除提示误判为未知页面 | 查看 /api/jobs/<job_id> 的 error_code、error_message 和 remote_attempt.prompt_text；若为“本帖已经删除，错误权限代码255”，部署包含该修复的版本并等待下一次执行，任务会终止为 THREAD_DELETED，不再继续退避 |
| 节点健康但同一 Job 反复使用或丢失节点历史 | 节点健康探测只验证固定探测帖，不等价于目标帖、账号和 Cookie 可用；旧 Runner 也可能用过期快照覆盖历史 | 同时检查 /api/proxy-pool/health?refresh=true、/api/jobs/<job_id> 和 /api/jobs/<job_id>/events；重点查看 remote_attempt.nodes_tried、account_ids_tried、prompt_text |
| 任务一直 queued | Daemon 未启动 | `uv run yamibo-daemon` |
| 任务 failed + LoginRequired | Cookie 过期 | 更新 `data/cookies/` 下对应账号的 cookie 文件 |
| 任务 failed + RemoteMaintenance | 论坛维护中 | 等待维护结束（5:30-6:30 UTC+8） |
| 任务 partial | 部分图片下载失败 | 在本地帖子阅读预览对具体缺图使用「立即补图」；仅在正文或楼层也需要更新时才重新同步整帖 |
| 单图补取持续失败 | 第三方外链永久失效、站内附件暂时受维护/反爬限制，或 Cookie 无权限 | 外链确认一次失败后保留缺失记录；站内 `forum.php?mod=attachment...` 或 `/data/attachment/` 图片按 `waf_response`、`html_response`、`truncated_image` 分别检查 Cookie、维护状态、代理和传输完整性 |
| LLM 解析失败 | API Key 未配置或无效 | 检查 `llm.api_key` 配置 |
| Web 控制台无法访问 | 端口被占用 | 修改 `web.port` 配置 |
| RAG 向量索引失败 | SQLite 下 `sqlite-vec` 无法加载，或 PostgreSQL 下 `pgvector` / embedding 配置缺失 | 检查向量扩展、`YAMIBO_RAG_API_KEY`（或明确的 LLM 回退配置）和 RAG 页面中的失败提示 |

单图补取失败后，无需进入容器查看 stdout。优先查询：

```bash
curl -fsS 'https://<部署域名>/api/logs?job_id=<job_id>&event_type=image.download.result&limit=100' | jq
curl -fsS 'https://<部署域名>/api/jobs/<job_id>/events' | jq
curl -fsS 'https://<部署域名>/api/jobs/<job_id>' | jq '.artifacts.image_download_summary, .artifacts.image_download_diagnostics'
```

`/api/logs` 是进程内最近 500 条实时日志，服务重启后会清空；Job events 和 Job artifacts 持久化在数据库中，适合事后排查。
